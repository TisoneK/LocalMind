TASK: Agent quits after satisfying ONE part of a multi-part request ("doesn't work hard enough")

## Symptom (live, bankofai/glm-5.3-flash, user-observed 2026-08-31)
User prompt: "Arsenal livescore and news" — TWO sub-goals: (1) live score, (2) news.
Agent ran web_research ONCE, got the live score (Aston Villa 0-0 Arsenal, standings) from
Sofascore, answered the score well — then ended the turn with:
  "I couldn't pull additional news headlines in this pass — the live match is the main
   story right now. ... the Sofascore match page is tracking it live."
i.e. it satisfied sub-goal (1), abandoned sub-goal (2), and told the user to look it up
themselves. Only 1 tool step, 2 iterations. The answer literally CONFESSES the gap.

## Root cause (hypothesis — verify)
The turn-completion seam classifies this turn as ANSWER/recovery=NONE because final_text is
substantive (the score). There is no signal that the answer ADMITS an unmet, explicitly
requested sub-goal while tools that could satisfy it (web_research/web_search) are still
available. So the loop ends instead of continuing.

Seam: backend/src/core/agent/turn_outcome.py -> classify_turn_outcome(...). It ALREADY has an
`is_follow_through_failure` param that maps INCOMPLETE -> Recovery.FORCE_TOOL. The gap is
DETECTING this case and setting that flag. Find where is_follow_through_failure is computed in
backend/src/core/agent/loop.py (search "is_follow_through_failure" / "follow_through") — that
detector currently fires on mid-turn "let me try the next source"-style text, NOT on a FINAL
answer that concedes an unmet requested part.

## Fix direction (general + model/env-agnostic — NOT sports-specific, NOT a one-off patch)
1. Prompt (backend/src/core/agent/prompts.py, the native_bootstrap prompt I rewrote): add a
   persistence clause to the converse-or-act section, e.g.:
   "A request with multiple parts (X and Y) is not done until every part is answered. If a
    tool can get a missing part, call it — never tell the user to look it up themselves or
    defer it to 'next pass'."
2. Detector: on the FINAL answer, if it contains an explicit incompletion admission about a
   requested item ("couldn't pull/get/find/fetch X", "in this pass", "you can check X
   yourself/on <site>") AND the objective had multiple conjoined asks, classify INCOMPLETE
   with Recovery.FORCE_TOOL so the loop runs another tool for the missing sub-goal. Keep it
   language-general (the reasoning_effort retry precedent shows English-only matching is a
   flaw). Prefer detecting "requested item still unmet" over keyword-spotting where feasible.
3. Guardrail: don't force-loop forever — cap the follow-through retries (respect the existing
   iteration budget / describe_tool credit machinery in loop.py) and only fire when a relevant
   tool exists for the missing part.
