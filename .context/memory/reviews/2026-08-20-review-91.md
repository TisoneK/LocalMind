# Review — Session 325: Windows-relative backslash paths survive whole in the file reader

- **Date:** 2026-08-20
- **Agent:** Buffy / deepseek/deepseek-v4-flash (per system prompt)
- **Target:** user's live Windows trace (bankofai/deepseek-v4-flash) — the agent wrote
  `dev\test-run\notes.txt` ("Wrote 19 bytes to C:\Users\tison\Dev\test-run\notes.txt") and the
  immediate read of the same relative path failed with `not_found`, ending the turn without
  completing the request.
- **ADR:** none (fix, not architecture)

## Executive Summary

The file reader's path extractor only accepted forward slashes in bare paths, so a
Windows-RELATIVE path (`dev\test-run\notes.txt`) was truncated at the backslashes down to the
bare filename `notes.txt`, which was then looked up under home/cwd and reported `not_found` —
even though the writer had just created the file. Session 264 fixed drive-ABSOLUTE paths with a
dedicated Windows-drive pattern that runs before the bare pattern, but the bare char class
stayed forward-slash-only, leaving relative Windows paths broken — the same disease one level
down. The bare char class now also accepts backslashes, so the full relative path survives as a
single candidate.

## Discovery

- Traced the failure chain in `file_reader.py`: `_PATH_PATTERNS[2]` is
  `((?:~/|\.{0,2}/)?[\w.\-/]+\.(?:{_READ_EXTS}))` — `[\w.\-/]` is forward-slash ONLY. On
  `dev\test-run\notes.txt` the regex backtracks to match just `notes.txt` (the dot + ext anchor),
  which resolves under home/cwd and never exists. Confirmed by direct extraction of the repro
  string: pre-fix candidate was `notes.txt`, not the full path.
- The write side was never implicated: `file_writer.resolve_write_path` handled the same string
  correctly (named-folder anchor `dev` → `Dev`), which is why the trace showed a successful write
  followed by a failed read.
- macOS verification caveat: POSIX treats backslash as a filename character, so
  `Path('dev\test-run\notes.txt')` is a SINGLE component on macOS while Windows splits it into 3
  (dev, test-run, notes.txt). A fully faithful on-disk read-back is therefore impossible on macOS;
  verification relied on (a) unit tests asserting the extraction, and (b) the unchanged stdlib
  pathlib resolution (`home/` + `cwd/` joins, first-existing-candidate wins) that S264 already
  relied on. A byte-level hex comparison (`full_cwd` vs literal string) proved the earlier
  `not_found` results were test-harness artifacts (shell-quoting backslash doubling, then the
  POSIX single-component join), not a code defect.

## Fixes Applied

1. **`file_reader.py`** — bare-path pattern char class widened `[\w.\-/]` → `[\w.\\\-/]`
   (forward slashes AND backslashes); NOTE ON ORDER comment updated to document the S325 case
   alongside the S264 absolute-path ordering requirement.
2. **Tests (`test_file_reader.py`)** — 3 new regression tests: (a) `dev\test-run\notes.txt` kept
   whole inside prose, (b) not truncated to the bare filename (single full-path candidate), (c)
   mixed separators — Windows-relative in prose + forward-slash relative still working.

## Baseline / Verification

  clean on touched files. All prior S264 contracts hold: Windows absolute path first candidate,
  spaces in path, forward-slash absolute, Unix absolute, bare filename, no-path prose.
- Extraction proven on the exact repro: `ABS first: True`, `REL == [full path]`, UNIX/BARE/PROSE

# Follow-up (same session, same Windows trace): verification reports the real file size

After the S325 fix shipped, the user restarted and re-ran the task on Windows — it **completed**
end-to-end (mkdir → file_write 19 bytes with `[VERIFICATION]` → file_task read-back "hello from
deepseek" → final answer confirmed match). The S325 fix held live. The trace also exposed a
second, cosmetic-but-real bug: `[VERIFICATION]: file_write confirmed — 79 chars verified on disk`
for a 19-byte file.

**Root cause:** `loop._verify_tool_result` computed `actual_len = len(verify_result.content)` —
the length of the file_task READ-BACK REPORT ("File: <path>\nSize: N bytes\n\n<preview>"), not
the file's content. Two consequences: (a) the surfaced number was factually wrong (~79 "chars"
for a 19-byte file); (b) the ~60-char header skewed the truncation heuristic (`expected_len > 100
and actual_len < expected_len * 0.5`) — a 200-char write that landed as 90 bytes produced a
~150-char report and escaped the 50% loss check.

**Fix shipped (`8460829`):**
1. `file_reader.file_task` surfaces `size_bytes` in ToolResult metadata.
2. `_verify_tool_result` reads `metadata["size_bytes"]` (falls back to report length only for
   callers that don't provide it), guards the empty-file check with `expected_len > 0` (a
   deliberately empty write is not reported as a failure — the old empty branch was effectively
   dead because a report string is never 0 chars), and reports "N bytes verified on disk".
3. `prompts.py` VERIFY section updated to "N bytes on disk".
4. Tests: the existing no-readback-directive fake now carries `metadata["size_bytes"]`; two new
   regressions — (a) a 19-byte file yields "19 bytes verified on disk" (never "79 chars"); (b) a
   200-char write landing as 90 bytes is flagged "may be truncated" (previously passed).

**Verification:** full backend **2083 passed / 2 skipped / 0 failures** (2081 + 2 new); ruff
clean (one pre-existing I001 import-sort nit in the touched test file auto-fixed).

**Caveat noted:** this trace exercised the S264 ABSOLUTE-path handling — the model used forward
slashes for mkdir and `C:\...` absolute paths for write/read. The S325 relative-backslash path
(`dev\test-run\notes.txt`) remains unit-covered but has not yet been exercised by a live Windows
run; the mocked-WindowsPath harness from step 2 above would close that gap durably.
