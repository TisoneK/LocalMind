# Review 71 — Session 302: warm Parent Kernel phase one

- **Date:** 2026-08-20
- **Agent:** Buffy | **Model:** openai/gpt-5.6-luna | **Platform:** macOS (Darwin, local) | **Role:** engineer | **Core:** 0.8.0
- **Task:** User proposed initializing the parent once at server boot, keeping it ready across turns, and selected phase one: eliminate the per-turn parent-initialization call.

## Root cause addressed

The runtime had a reusable adapter and `AgentLoop`, but still performed a parent JSON initialization model call on every user turn. That call mixed routing, planning, and direct-answer generation. The parent was not actually warm: static identity/tool context was rebuilt in the request path, and the live request then paid another meta-call before normal execution.

## Product implementation

- Added `ParentKernel` as server-lifetime state containing the active adapter, compiled parent contract, registered tool metadata, settings signature, and readiness/degraded state.
- Application lifespan now builds the kernel before accepting requests, including cloud adapters. Provider warmup is best-effort; an unavailable/unconfigured provider logs degraded startup and the first real request retries lazily.
- Kernel invalidation tracks adapter/model, a non-secret API-key fingerprint, thinking/reasoning settings, shell enablement, and Ollama context settings.
- Added a `BaseAgent.run()` context override so the boot-compiled parent contract reaches the loop without rebuilding the parent context every turn.
- Removed the runtime's generic `context_builder.build()` prompt assembly for parent turns. Each turn now carries a bounded recent user/assistant tail, the current message, optional bounded attachment content, dynamic environment/workspace state, and per-turn memory/evidence.
- Removed the old runtime conversational fast-path implementation entirely. All user turns enter the same native parent loop; there is no capability phrase map or canned response branch.
- Parent-native first calls skip the retired JSON initializer and accept ordinary prose or native tool calls. The bootstrap native surface contains only `describe_tool`; the model loads a core or long-tail capability schema before executing it. Core tool metadata compatibility is preserved while the loop infers the loaded schema for the next call.
- Preserved recovery, completion-floor, safety, persistence, workspace, lifecycle, and stage-timing behavior. The old generic builder symbol remains import-compatible for integrations/tests but is not called by the parent runtime.

### Before/after interpretation

The documented pre-change GLM traces showed every turn entering the parent initializer and the exact capability flow requiring a separate generic direct boundary. This phase removes that initializer entirely. The first post-change GLM trace initially caught the duplicate generic prompt, and the final post-change trace proved the corrected boot/kernel/native boundary. Tool selection was live-verified on Zen because z.ai was rate-limited during its tool request and Cerebras returned payment-required.
