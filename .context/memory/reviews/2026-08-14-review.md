# Freebuff / Codebuff orchestration review

## 1. Executive Summary

The uploaded research identified the right architectural direction, but it mixed three evidence levels: official Codebuff agent definitions/docs, product-level Freebuff claims, and reverse-engineered Freebuff API observations. Official sources confirm the important reusable pattern: agents are the composable unit; each agent has a model, scoped tools, an allowlist of spawnable agents, a spawner prompt, an instructions prompt, an output mode/schema, and optional programmatic generator control. Child agents default to isolated context and return a final message or structured output rather than their full history.

LocalMind already implements most of the high-value ideas: directory-based agents, scoped toolsets, per-agent model routing, bounded delegation packets, handoff delegation, concurrent delegation, a gated inline context-pruner, fixed reviewer output schema, task-type routing, acceptance verification, and delegation lifecycle observations. This review found no reason to copy Codebuff's hosted session/API metadata protocol into the local runtime.

The remaining architectural risks are:

1. The legacy `should_use_sub_agents()` heuristic still runs before the ADR-8 agent-selection path and can route complex work through the older `SubAgentType` system.
2. `delegate_parallel` isolates run metadata but not the filesystem/workspace; concurrent mutating children can conflict.
3. Delegation metadata is bounded, but the parent-facing `ToolResult.content` can include full child prose and parallel summaries, so child output is not uniformly bounded at the context boundary.
4. LocalMind has a ReviewerAgent and acceptance gate, but no universal runtime rule that automatically invokes a read-only reviewer after every mutation.
5. The uploaded claims about `/api/v1/agent-runs`, `codebuff_metadata`, `ancestorRunIds`, and A2A endpoints were not verified in official Codebuff/Freebuff documentation and should remain untrusted reverse-engineering notes, not implementation requirements.

## 4. Verified orchestration contract

### Agent definition

The official definition is declarative and composable. The relevant fields are:

```ts
const definition: AgentDefinition = {
  id: 'simple-code-reviewer',
  displayName: 'Simple Code Reviewer',
  model: 'anthropic/claude-sonnet-4.5',
  toolNames: ['read_files', 'run_terminal_command', 'code_search', 'spawn_agents'],
  spawnableAgents: ['codebuff/file-explorer@0.0.2'],
  spawnerPrompt: 'Spawn when you need to review local code changes',
  systemPrompt: '...',
  instructionsPrompt: '...',
}
```

The definition also supports `includeMessageHistory`, `outputMode` (`last_message`, `all_messages`, or `structured_output`), `outputSchema`, and `handleSteps`. This is stronger evidence than the uploaded claim that agents are merely named tool bundles: prompt, model, tool access, child allowlist, context policy, and return contract all belong to the agent.

### Exact spawn command

The official walkthrough uses this shape:

```ts
const { toolResult } = yield {
  toolName: 'spawn_agents',
  input: {
    agents: [
      {
        agent_type: 'codebuff/file-explorer@0.0.1',
        prompt: 'Find files related to the changed code',
      },
    ],
  },
}
```

Multiple entries in `agents` run in parallel. Sequential behavior is achieved by spawning one agent, consuming its result, then spawning the next. `spawnableAgents` is an allowlist; the orchestrator cannot freely invoke every published agent.

### Exact generator controls

Official `handleSteps` examples use:

- `yield { toolName, input }` to execute a deterministic tool call.
- `yield 'STEP'` to run one model step and return control to the generator.
- `yield 'STEP_ALL'` to let the model continue until it naturally stops.
- `set_output` to publish a final structured result to the parent.
- `return` to stop a programmatic flow.

This lets an agent force reconnaissance, branch on tool results, fan out work, run a selector, and then release control back to the model. It is not just prompt chaining.

### Exact specialist contracts

| Agent | Official tools / behavior | What LocalMind should copy |
|---|---|---|
| Base | `create_plan`, terminal, file edits, agent lookup/spawn, subgoals, search, read, think, `end_turn`; spawns file explorer, picker, researcher, thinker, reviewer, context pruner | Declarative agent metadata, child allowlists, final-output boundary |
| Researcher file explorer | `spawn_agents`, `set_output`; spawns `researcher-file-picker` children in parallel | Programmatic fan-out plus one structured report |
| File picker | `find_files` only; one deterministic call then concise report | Very narrow mechanical worker, not a general model |
| Code searcher | `code_search`, `set_output`; runs multiple queries and aggregates JSON results | Batch mechanical queries with a fixed return shape |
| Reviewer | `run_file_change_hooks`, `end_turn`; `includeMessageHistory: true`; cannot modify files | Read-only quality gate with checks before critique |
| Context pruner | `set_messages`; inherits history; deterministic passes simplify terminal results, large tool results, and old messages | Inline mutation only for a tightly gated, fail-safe specialist |
| Editor | read/write/replace/search/terminal/spawn/output tools; inherited history; step limit; returns edits in structured output | Editing remains with a context-rich agent, not a blind write sub-agent |
| Best-of-N thinker | spawns N thinkers, then a selector; bounds N and emits the selected answer | Parallel fan-out + selector only for high-value tasks |

The public official sources identify `basher` as a built-in terminal-command agent, but the reviewed public pages did not expose a stable basher versioned definition or an exact basher prompt. The safe verified fact is its role, not an invented prompt or schema. Likewise, `file-picker` officially uses `find_files`; the uploaded research's generalized `read_files` assignment is not exact for that published version.

### Context and return semantics

The default is isolated child context: `includeMessageHistory` is false unless an agent opts in. The base agent explicitly says spawned agents start with no context and must receive sufficient instructions. A child can return only its last message, all messages, or structured output. The official launch article explicitly describes the orchestrator receiving final output rather than every child tool result/reasoning message.

The reviewer is an important nuance: its definition opts into parent history and is read-only, while the file explorer and code-searcher start fresh and receive bounded prompts. Context inheritance is a per-agent contract, not a universal property.

## 5. Findings

### Critical

None.

### High — architectural, do not implement as an opportunistic fix

#### H1. Legacy decomposition still bypasses ADR-8

`core/engine/_pipeline.py` still calls `should_use_sub_agents()` before the modern `select_agent_by_task_profile()` path. That heuristic can invoke the older `SubAgentType` registry and `decompose_task()` path. LocalMind therefore has two active orchestration systems: the ADR-8 agent-centric `BaseAgent` path and a pre-loop keyword/complexity path. This is the largest remaining mismatch with Codebuff's agent-as-composable-unit model.

**Recommendation:** replace the legacy branch with a dispatcher-produced task contract and agent-owned `delegate`/`delegate_parallel`; preserve a temporary shadow metric and a compatibility fallback until real-model tests cover multi-domain coding, research, and mixed tasks. Do not remove the old path in a broad refactor without a migration test matrix.

#### H2. Parallel children share the real workspace

`delegate_parallel` gives children isolated `ContextVar` run/depth state, but child agents still operate against the same filesystem and process environment. Codebuff's Freebuff README specifically describes Desktop parallel work as isolated workspaces; generic parallel child execution is not equivalent to that product surface. Concurrent coding children can overwrite files, race on tests, or observe each other's partial state.

**Recommendation:** initially restrict `delegate_parallel` to read-only/research/review tasks, or add explicit per-child workspace isolation with a merge/apply stage before allowing concurrent mutation. The existing proposal registry isolates staged edits but does not isolate arbitrary shell/file/process side effects.

### Medium — safe follow-up candidates

#### M1. Parent-facing child output is not uniformly bounded

LocalMind's `DelegationResult.to_metadata()` caps previews at 500 characters, but `delegate` returns the full child response in `ToolResult.content`, and `delegate_parallel._build_summary()` includes every completed child output. The child history is isolated, but a large final response can still inflate the parent context.

**Recommendation:** make the result boundary explicit: cap content, preserve full output in a run-local artifact when needed, and return a bounded structured envelope (`status`, `agent`, `run_id`, `summary`, `evidence_refs`, `truncated`). Keep fixed schemas for specific agents and reject/repair invalid structured output before it reaches the parent.

#### M2. Reviewer invocation is not a universal runtime gate

LocalMind has a read-only `ReviewerAgent`, fixed output schema, and acceptance verification, but the engine does not universally spawn the reviewer after every mutating coding run. Codebuff's official reviewer definition describes when the base agent should spawn it and gives it a no-write tool surface; that is a prompt/agent contract, not evidence of a hidden hosted API gate. LocalMind's stronger acceptance gate can remain the primary correctness mechanism, with reviewer delegation added for code-quality review where appropriate.

**Recommendation:** design this as a policy stage: mutation → deterministic verifier always; reviewer for configured/high-risk changes. Do not make every trivial write pay a second model call.

#### M3. Run-tree data exists locally but not as a durable session protocol

LocalMind has `AgentRunContext`, `run_id`, `parent_run_id`, context-local depth, child lifecycle observations, and bounded delegation metadata. That is enough for local correlation. Official sources reviewed do not establish that Freebuff's internal transport requires the uploaded `/api/v1/session`, `/api/v1/agent-runs`, `codebuff_metadata`, or `ancestorRunIds` protocol.

**Recommendation:** keep LocalMind's simpler internal run contract. Add persistence/API projections only if the UI needs replay, billing, cancellation, or cross-process recovery.

### Low / Nice to Have

#### L1. Versioned agent definitions are useful, but not required locally

Codebuff's publisher/version IDs make agent capabilities discoverable and reproducible. LocalMind's auto-discovered Python directories are a good local equivalent; a lightweight `AgentManifest` could add model, capability, output mode, and spawnable-agent metadata without copying the hosted store.

#### L2. Generator-style deterministic orchestration is a useful future abstraction

LocalMind already has deterministic dispatcher signals, execution graphs, acceptance gates, and delegation primitives. A future `AgentPlan`/step runner could expose Codebuff-like `STEP` and `STEP_ALL` semantics for recurring workflows, but this should follow the legacy-path removal rather than add a third orchestration framework.

## 6. Unsupported or overstated claims in the uploaded research

- **A2A protocol:** no official Codebuff/Freebuff source reviewed here documents Google A2A `/.well-known/agent.json`, `/tasks/send`, or `/agents/register` as the internal orchestration mechanism. Treat this as unverified unless the upstream source is produced.
- **Session/run HTTP endpoints and metadata:** searches found third-party reverse-engineering/proxy projects discussing `/api/v1/agent-runs`, `codebuff_metadata`, and `ancestorRunIds`, but not official product documentation. These may describe a private hosted transport or a proxy implementation; they are not a LocalMind design requirement.
- **Universal mandatory reviewer:** official reviewer metadata recommends spawning it after significant changes and makes it read-only; the reviewed sources do not prove a universal server-side enforcement rule for every edit.
- **Unlimited arbitrary nesting:** official definitions show allowlisted `spawnableAgents`; the base prompt says agents can spawn others, but the reviewed public contract does not establish unlimited depth. LocalMind's explicit depth cap is safer.
- **Exact basher prompt/schema:** the official overview verifies basher's purpose, but no stable public versioned definition was found in this research pass. Do not fabricate exact instructions.
- **`@filename`, `@AgentName`, `!command`, `/bash`, and `/init`:** `/init` and custom-agent invocation are documented; the other interaction syntax should be treated as product-surface behavior that needs source-specific verification, not assumed to be part of the core sub-agent protocol.
