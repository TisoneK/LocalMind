# Review 68 — Session 299: structured tool failures bypassed recovery

- **Date:** 2026-08-19
- **Agent:** Buffy | **Model:** openai/gpt-5.6-luna | **Platform:** macOS (Darwin, local) | **Role:** engineer | **Core:** 0.8.0
- **Task:** User reported that thinking and recovery were broken. Investigate the reasoning/recovery boundary and fix the live-proven failure without adding another provider- or tool-specific prompt patch.

## Root cause

`dispatch_with_retry()` returned `(result, False, attempt)` whenever dispatch itself completed, even when a tool returned a structured `ToolResult` with `success=False`. The AgentLoop therefore treated failed actions as completed actions: it could run Thinker against an error observation, skip failure-memory/streak recovery, and miss the completion-floor failure signal. This was the shared contract defect underneath the visible thinking/recovery failure.

## Fix (`e806f07`)

- `dispatch_with_retry()` now returns `failed=True` when the result is `None` or `result.success is False`, including non-retriable structured errors.
- Added regression coverage for the dispatch contract and the real loop boundary.
- The loop-level regression verifies that structured failures produce a failed tool event, suppress `agent_thinker_start`, record `tool_failure`, and still allow the model to continue to a recovery answer.
- Kept the completion-floor observation check as a defensive fallback for command-level failures from tools that may still encode failure in output text.
- Updated the code-execution dispatch expectation so rejected structured inputs remain failures even when retries are correctly skipped.
