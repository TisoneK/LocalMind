## Root Cause (confirmed, not guessed)

`MAX_ITERATIONS = 3` (lowered in Session 31 to fit a 90s wall-clock cap)
was too low for multi-step tasks. The user's "Create hello world repo"
scenario needed 6 steps:
1. Check if dir exists (recon)
2. Check dir contents (recon)
3. Check git available (recon)
4. `git init` (work)
5. `file_write hello.py` (work)
6. `git add + commit` (work)

The model did 3 reconnaissance calls (doing exactly what we want —
checking state before acting) and hit the cap at step 3, before reaching
the actual work. The Session 31 cap of 3 punished the model for being
thorough.

**The user's insight about the misdiagnosis pattern was correct**: the
earlier "overload" / "context overflow" / "tool output too large" messages
from Sessions 21-31 were almost certainly this same iteration-limit issue,
mis-explained by the fallback text. The fallback guessed at causes instead
of reporting the actual cause (`trace.hit_limit = True`).

## Fixes Applied

### Fix 1: Raise + make configurable the iteration limit

**File:** `backend/src/core/agent/constants.py`

- `MAX_ITERATIONS`: 3 → 8 (configurable via `LOCALMIND_MAX_ITERATIONS` env
  var, floor 1, invalid values fall back to default)
- `MAX_WALL_CLOCK_SECS`: 90s → 180s (configurable via
  `LOCALMIND_MAX_WALL_CLOCK_SECS` env var, floor 30s)

8 iterations gives room for: reconnaissance (2-3 calls) + actual work
(3-5 calls) + verification (1-2 calls). The wall-clock cap (180s) is the
real safety net — it prevents a small model from spinning forever even
with 8 iterations available.

Note: `config.py` has `localmind_agent_max_iterations` (default 6) but
that value was never read — `constants.py` hardcoded 3. The env var is
now the actual source of truth. A future session could consolidate.

### Fix 2: Hit-limit-aware fallback messages

**Files:** `backend/src/core/agent/loop.py` (`_summarize_trace_for_user`),
`backend/src/core/engine/_pipeline.py` (engine fallback)

When `trace.hit_limit` is True, the fallback now explicitly says:
> "I hit my iteration limit (N iterations) before completing the task.
> This is NOT a model overload or context-overflow issue — I simply ran
> out of steps."

And suggests: "Tell me to 'continue' — I'll pick up where I left off."
Plus mentions the `LOCALMIND_MAX_ITERATIONS` env var for configurability.

When `hit_limit` is False (model genuinely failed), the fallback keeps
the evidence-based message from Session 31 (surface actual tool outputs,
don't guess).

This kills the misdiagnosis pattern: the fallback now reports the ACTUAL
cause when the iteration cap is hit, instead of guessing "overload."

### Fix 3: "Check before acting" universal workflow constraint

**File:** `backend/data/workflows/safety.md` (new)

The universal rule: **before ANY tool invocation that creates, writes,
modifies, or deletes something, you MUST first check whether the target
already exists or has content. Your action must depend on what you find
— never on what you assumed or expected.**

This is a constraint, not a script. The model decides the specific check
and the specific action. The constraint is: don't act blind.

Per-tool guidance:
- **Shell**: before `mkdir`, check if dir exists; if non-empty and
  unrelated, create a subdirectory instead. Before `rm`, list first.
- **File tools**: before `file_write`, check if file exists; if so, READ
  it first and decide (overwrite/append/different path). Never blind-
  overwrite.
- **Code exec**: code that writes to disk should check state first
  (`os.path.exists`).
- **Web tools**: before feeding results into the next step, check the
  size/shape — don't dump 5000 tokens of raw HTML into the model.
- **Memory**: before storing, check for duplicates/conflicts.

Includes the "subdirectory adaptation" the user specifically identified:
when the target is non-empty and unrelated to the task, scope work into a
subdirectory instead of dumping alongside existing files.

### Fix 4: Inject safety workflow into agent prompt

**File:** `backend/src/core/agent/prompts.py` (`build_agent_system_prompt`)

The safety workflow is now injected into the agent system prompt for ALL
agent intents (SHELL, FILE_WRITE, FILE_EDIT, FILE_TASK, CODE_EXEC,
WEB_SEARCH, WEB_FETCH, BROWSE, MEMORY_OP). The injection extracts the
"The universal rule" + "How it applies per tool" + "What you must NOT do"
sections (skips the header, "what done looks like", "why this exists", and
"learning step" — those are for humans reading the file, not for the model
every single turn).

## Lessons Learned (this session)

1. **Honest error messages enable diagnosis.** The Session 31 adapter fix
   made the terminal work and the fallback honest ("I hit the iteration
   limit"). That honesty is what let the user diagnose the remaining issue
   precisely. If the fallback had still said "overload," the user would
   have been stuck guessing.

2. **The misdiagnosis pattern was the real bug.** Sessions 21-31 kept
   guessing "overload" / "context overflow" / "tool output too large" when
   the actual cause was the iteration cap. The fix isn't just "raise the
   cap" — it's "make the fallback say 'iteration limit reached' when
   that's the cause, so we stop misdiagnosing."

3. **"Check before acting" is a universal rule, not a per-tool fix.** The
   user explicitly asked for this to be a workflow constraint, not
   re-implemented separately for shell, files, and search each time a gap
   is discovered. The `safety.md` workflow file is the constraint; the
   prompt injection enforces it across all tools uniformly.
