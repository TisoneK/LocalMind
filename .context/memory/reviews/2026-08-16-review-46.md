# Review — Fixed "empty_response" after long thinking on z.ai/GLM (Session 256)

**Agent:** Buffy · **Model:** deepseek/deepseek-v4-flash · **Date:** 2026-08-16 · **Type:** bug fix (user-reported live failure)

## Summary

The user's real turn failed on z.ai/glm-4.5-flash with thinking ON: "Create a recipe on desktop" → iter-1 ran `shell(Get-ChildItem "C:\Users\tison\Desktop")`, iter-2 streamed a long reasoning burst (169s thought process at 0.89 tok/s) then returned **no content and no tool call**, and the loop classified it as `empty_response` and failed the whole turn. **This is the same pattern I saw in Session 254's live traces and mislabeled as "transient free-tier throttling"** — it is a real interaction bug between thinking-on (ADR-41) and the loop's empty-response guard.

## Root cause

The loop's empty-response check (`loop.py`, Session 115 guard) tests the **text buffer only** (`initial_buffer`). With thinking re-enabled, a slow free tier sometimes produces a stream of reasoning deltas (`reasoning_content`) with no `content` and no `tool_calls` delta — the model "thinks but doesn't act". The reasoning was forwarded to the UI as live thought, but the empty guard saw no text → `agent_loop_empty_response` → honest evidence fallback → the turn dies even though the model was mid-thought.

## Fix

**Bounded recovery instead of instant fail when the stream contained reasoning:**

- Track `_streamed_reasoning` per iteration (set when a non-empty `chunk.thinking` streams — same guard shape as the Session 254 isinstance guard, so MagicMock stubs don't trip it).
- In the empty-response block, after the existing iteration-0 forced-tool nudge: if `_streamed_reasoning` and `trace.empty_reasoning_recoveries < _MAX_EMPTY_REASONING_RECOVERIES` (1), do **one** retry with a continue-nudge ("you started reasoning but returned no answer and no tool call — continue now: call the tool you need or give the final answer"), appending an empty assistant frame first (message-role alternation for strict providers). Emits `empty_reasoning_recovery` obs event.
- A **second consecutive empty still fails fast** — the think-only protection from the original disable (the reason the disable existed) stays intact, and the wall-clock cap still bounds the whole turn.

New `AgentTrace.empty_reasoning_recoveries` counter (`core/agent/models.py`).

## Tests

`tests/adapters/test_thinking_policy_adr41.py` — 2 new deterministic tests:
1. `test_empty_after_reasoning_recovers_with_nudge` — stub: tool call → reasoning-only → final answer. Asserts the turn completes, 3 LLM calls happen, and reasoning from both calls reaches the output.
2. `test_second_empty_after_reasoning_still_fails_fast` — stub: tool call → reasoning-only ×2. Asserts the honest evidence fallback fires after exactly one nudge.

Full suite **1,799 passed** (2 new; 4 pre-existing env-gated `test_shell.py` failures, same as baseline). Ruff clean. Live reproduction was not attempted: the empty-after-reasoning is probabilistic on the free tier and cannot be forced on demand; both branches are exercised deterministically by the stubs.

## Notes for future sessions

- **When a live trace shows a harness fallback firing, that is a harness bug to fix — not an environment excuse.** Session 254 saw this exact evidence-fallback firing after thinking streamed; I wrote it off as throttling. Logged as a lesson in sessions.md.
- The empty guard is text-only by design (thinking never drives tool detection), but reasoning IS progress for UX recovery — different concerns need different handling, now separated.
- If the free tier's "thinks but doesn't act" gets worse, the lever is a real reasoning-effort/budget param for GLM-5.2+ (`reasoning_effort`, Session 254) — GLM-4.5-flash has none.
