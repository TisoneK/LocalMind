# Review — Post-tool provider-limit handling

## Executive Summary

A reported Cerebras rate-limit card followed a successful `web_search` tool call. The provider error came from the next model request, which was responsible for synthesizing the tool evidence; the loop treated that retryable post-tool failure as a fatal turn error and discarded the successful evidence. The agent loop now preserves evidence after retryable provider failures that occur only after successful tool work, while retaining the existing fatal error path for pre-tool and permanent failures.

## Discovery Phase

- The UI trace showed `1 tools / 1 done` and an `evidence` event for `web_search` before the rate-limit card.
- `AgentLoop` buffered provider errors during the follow-up stream and unconditionally yielded `StreamChunk.error`.
- `AgentRuntime` forwards any error chunk directly to the SSE normalizer, so the frontend correctly rendered the error it received—but the loop had incorrectly classified the whole turn as failed.
- The adapter's retry and canonical error classification remain provider-agnostic; the reported 429 is a real provider response, not a tool failure.

## Finding

### Medium — post-tool retryable provider errors erased successful evidence

**Impact:** A completed search or other tool operation appeared in the workspace, but the chat displayed “Unable to get a response” and offered only provider retry actions. Users could not use the verified result even though the tool had completed successfully.

**Root cause:** The loop's text-stream error branch treated every provider error as terminal without checking whether the trace already contained successful tool evidence.

## Fix Applied

- Normalize the provider error at the loop boundary.
- When the error is provider-originated and retryable, and at least one tool step succeeded, emit `agent_loop_degraded` and return `_summarize_trace_for_user(...)` with an explicit final-synthesis rate-limit explanation.
- Do not attach `StreamChunk.error` in this degraded path, preventing the frontend from rendering a false whole-turn failure card.
- Keep permanent provider errors and errors before successful tool evidence on the existing error path.
- Added a regression test covering successful Cerebras-style `web_search` followed by a retryable 429.
