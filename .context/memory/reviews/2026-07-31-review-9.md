# Session 52 Kickoff Review — Capability-Oriented LocalMind Direction

## Executive Summary

Kickoff-only architecture alignment session following the user's clarification
that LocalMind must support general desktop and knowledge-work tasks without
removing or weakening developer agents. No product files were changed.

The accepted direction is additive: preserve Coding, Debugger, Reviewer,
Verifier, and Analyst as first-class developer roles, while expanding LocalMind
through capability families and reusable tools. The long-term interaction loop
is Observe → Think → Decide → Act → Observe → Verify.

## Architectural Direction Confirmed

1. Developer agents remain first-class and are not replaced.
2. Agents are reusable decision/workflow roles; tools are controlled execution primitives.
3. Capability families should organize expansion: knowledge/reasoning, local information, internet, computer interaction, productivity, data, and connectors.
4. `Observe` is a foundational capability, covering system state, active window, screen, clipboard, running apps, notifications, and filesystem changes as permissions and platform support allow.
5. The safest next implementation step is to define capability-family and observation contracts before adding a broad new tool list.
6. Existing `Capability`, `TaskProfile`, `ExecutionGraph`, registry, delegation, and objective-runtime foundations should be extended rather than replaced.

## Findings

### Medium — capability taxonomy is not yet a durable contract

The existing capability model is useful but still mostly mirrors individual
routing/tool names. A capability-family registry should eventually define family,
operations, required tools, risk, confirmation policy, and supported agents.

### Medium — Observe remains a roadmap item

Browser screenshots and system/file/process signals exist in isolated paths, but
there is not yet one structured observation contract that feeds the next planning
turn across desktop/system state.

### Low — baseline todo-plan assertion drift

The one failing backend test should be reconciled in a future product session:
either update the assertion to the intentionally newer plan wording or restore
the previous label after checking the current UI contract. It was not changed here.

### Low — Ruff cleanup remains deferred

The three non-E501 findings are safe cleanup candidates, but changing them during
kickoff would mix baseline cleanup with architectural direction-setting.

## Recommended Next Steps

1. Design a small capability-family registry contract and tests.
2. Define a read-only `ObservationSnapshot` contract first, using existing
   system/browser/workspace signals without adding native input automation yet.
3. Add one vertical slice—local information/document discovery or observation—
   while preserving all developer-agent toolsets and routing tests.
4. Reconcile the todo-plan baseline assertion and clean the three non-E501 Ruff
   findings in a separate safe-fix session.
