# Review — Tool-context architecture: why tools cost 6.3k tokens/call, and the fix (Session 250, research-only)

**Agent:** Claude Code / claude-opus-4-8 · **Date:** 2026-08-16 · **Type:** research + design (no code, per user)

## Question (user)
"Why do tools need too much context/tokens when they do specific tasks? They are not agents, they are tools — the agent should feed instructions to the tool, not the tool feeding itself. It should carry only guardrails + how to behave; the agent holds full context and invokes only a SPECIFIC tool's context, not all of them for no reason."

## Findings (measured)
- The native `tools` param sends **all 30 tool schemas on EVERY model call = 25,339 chars ≈ 6,334 tokens**, re-sent every iteration, for every provider. It is now the single biggest per-call line item (bigger than the ~2.8k system prompt after ADR-39).
- The tool catalog appeared **three times**: (1) native `tools` param; (2) a text injection into the system prompt (removed Session 249, `a5c0a0b`); (3) the compact `agent_tool_list` inside the agent system prompt.
- The schemas are **kitchen-sink self-manuals**: `browse` = 17 params / 10 modes (2,172 chars); `git` = 10 params + 782 chars of prose enumerating every operation (1,943 chars); `delegate` describes 7 agents inline. This is literally "the tool feeding itself."
- **A lean index (name + one-line purpose) for all 30 tools = ~2,438 chars ≈ 609 tokens.** So ~**5,725 tokens/call (~90%) is reclaimable** if the full detail is loaded on demand instead of always.
- **The pattern already exists in-repo:** the `skill` tool. `available_skills_summary()` = a tiny always-visible index; `skill(name)` loads the FULL markdown on demand only when invoked. Tools should mirror this.

## Design (documented in ADR-40)
Two-tier tool context: **Tier 1** = a lean always-present index (name + one-liner + guardrails only); **Tier 2** = a specific tool's full schema/usage loaded on demand. Three mechanism options — (A) dynamic schema injection when a tool is selected [true progressive disclosure, +1 round-trip], (B) lean-but-callable schemas [simplest, no protocol change, ~50-70% of savings], (C) hybrid [core tools lean-always, long tail on-demand]. See ADR-40 for full tradeoffs.

## Recommendation
Ship **B first** (lean schemas — biggest safe win, no protocol change), **live-verify tool-calling** (right tool + valid args) on a provider with headroom — trimming schemas can regress tool SELECTION on a weak model (glm-4.5-flash), so unit tests are not enough. Then **C** (on-demand for the long tail). Keep guardrails + disambiguating hints; drop only the tutorial prose. Collapse the 3 copies to one source of truth.

## Guardrail for the implementing session
Do NOT claim a token win without a live tool-calling trace on a capable-enough model, and do NOT strip guardrails ("git --hard blocked", "read before edit") or the disambiguation weak models need to pick the right tool. Latency matters on free tiers (0.48 tok/s) — prefer B/C over A's round-trips there.
