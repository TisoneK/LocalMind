# Capability Gap Analysis — 2026-07-31

## Executive Summary

Session 40 cross-referenced the user's comprehensive capability assessment
against LocalMind's current codebase. LocalMind has a mature **coding agent**
core (14 tools, 4 agents, 5-step agent loop with workspace feedback, intent→task-type
routing, delegation) but is missing the **non-coding capability layer** that
would make it a general-purpose local AI assistant.

**The assessment's core thesis is correct:** LocalMind's toolset is heavily
biased toward software engineering. The world-interaction and knowledge-work
tools that distinguish a general assistant from a coding harness are almost
entirely absent.

## Findings by Severity

### Critical — Git tool is missing

**Impact:** Every coding action that touches the filesystem is followed by
"did that work? what changed?" The agent currently guesses — there's no
structured `git status`/`git diff` feedback loop. The `workspace_state.py`
service (ADR-5) takes snapshots but these are injected into context as text,
not as structured tool calls the agent can reason about.

**Recommendation:** Build a `git_tool.py` exposing the 9 operations the user
listed: status, diff, log, branch, checkout, commit, merge, stash, reset.
Wire it into `AGENT_ALLOWED_TOOLS` for CodingAgent. This is the single
highest-leverage addition — it closes the verification gap for every
coding task.

### Critical — Tester/Verifier agent is missing

**Impact:** LocalMind can write code but cannot systematically prove it works.
The user must manually run tests, check outputs, and validate behavior. This is
the "most important omission" from the user's analysis — and it's correct.
LocalMind currently has:
- `workspace_state.py` (snapshots git state → context)
- `code_exec.py` (can run Python)
- `shell.py` (can run any command)

But none of these are orchestrated into a verification agent. The model
CAN run `pytest` via shell, but there's no agent whose explicit responsibility
is "prove that what was built actually works."

**Recommendation:** Build a `VerifierAgent(BaseAgent)`. It should:
- Run the project's test suite (`pytest`, `npm test`, etc.)
- Parse test output for failures
- Reproduce reported bugs
- Run static analysis (`ruff`, `eslint`, `tsc`)
- Validate CLI/API behavior
- Report failures back to the orchestrator with structured diagnostics

Scoped tools: shell (for running test commands) + git (for diff) + file_reader
(for reading logs). This is Phase 1 of a broader testing capability.

### High — Process management is missing

**Impact:** Long-running processes (`npm run dev`, `uvicorn`, `docker compose`,
`pytest`, `playwright`) are treated as one-shot shell commands. There's no way
to start a server, wait for it to be ready, interact with it, and stop it.
Without this, the Verifier agent is crippled — it can run tests but can't
start/stop the services tests depend on.

**Recommendation:** Build a `process_tool.py` with start/stop/restart/status/
logs/wait. Use subprocess with PID tracking. This is a prerequisite for the
Verifier agent and for functional testing of web apps.

### High — Browser agent is underpowered

**Impact:** The `BrowserAgent` exists and `browser_agent.py` registers as
both a tool and agent, but the user's analysis correctly distinguishes between
"browsing the Internet" (WebFetch/WebSearch — present) and "operating a browser"
(click, type, select, navigate, inspect DOM, capture screenshot, inspect
network, read console — absent or limited). LocalMind can fetch pages but
can't interact with them like a real browser.

**Recommendation:** Evaluate the current `BrowserAgent` against the user's
10-point browser capability list (open page, click, type, select, navigate,
inspect DOM, capture screenshot, inspect network, read console). If it uses
Playwright or a Chrome DevTools protocol, many of these may be present but
undocumented. If not, this is a major build-out. The browser capability is
especially important for UI verification and reverse engineering.

### Medium — Patch/Diff tools are missing

**Impact:** The `edit_file.py` tool makes surgical string replacements within
files, but the agent has no way to reason about changes as patches — structured
representations of what changed, why, and how to revert. `git diff` could serve
this purpose if a proper Git tool existed.

**Recommendation:** Start with the Git tool (Critical). `git diff` + `git diff
--stat` + `git log` give the agent structured change visibility. A formal
Patch/ApplyPatch/Revert layer can be built on top of Git later.

### Medium — Diagnostics capability is missing

**Impact:** When something fails, the agent has to manually inspect files and
re-run commands. There's no structured error analysis — no `inspect_error`,
`analyze_traceback`, `inspect_test_failure`. The user's analysis correctly
places this as complementary to the Verifier agent.

**Recommendation:** Build `diagnostics.py` as a tool or as part of the
Verifier agent. At minimum: parse Python tracebacks (file, line, error type,
message), parse pytest output (failed tests, assertions, diffs), parse ruff/
eslint errors. This gives the Debugger agent (future) structured data to
reason about.

### Low — Non-coding capabilities are entirely absent

**Impact:** LocalMind is currently a coding agent, not a general-purpose
assistant. The user's analysis of non-coding capabilities (Knowledge &
Reasoning, Local Information, Computer Interaction, Personal Productivity,
Data, External Services, Observe) is aspirational — these capabilities
define what a general assistant IS.

**Recommendation:** Treat these as a **long-term roadmap**, not immediate
implementation targets. The highest-value non-coding additions are:
1. Computer Interaction (if LocalMind is to become a desktop assistant)
2. Observe (screen/active_window/clipboard — the foundation for "what's
   happening right now?")
3. Personal Productivity (calendar/tasks — makes LocalMind a daily driver)

These are better built as a **connector/plugin framework** (as the user
suggests) rather than hardcoded tools.

## Prioritized Implementation Roadmap

Based on the user's analysis cross-referenced against what exists, here's
the recommended implementation order:

### Phase A: Close the Coding Verification Gap (1-2 sessions)
1. **Git tool** — 9 operations (status, diff, log, branch, checkout, commit, merge, stash, reset)
2. **Process tool** — start/stop/restart/status/logs/wait for long-running processes
3. **Wire both into CodingAgent's scoped toolset**

### Phase B: Build the Tester/Verifier Agent (2-3 sessions)
4. **VerifierAgent** — runs tests, parses failures, checks acceptance criteria, runs static analysis, reports to orchestrator
5. **Diagnostics tool** — parse tracebacks, test failures, lint errors (structures failure data for the agent to reason about)

### Phase C: Upgrade Browser & Review (2-3 sessions)
6. **Upgrade BrowserAgent** — full DOM interaction, screenshots, network inspection, console reading
7. **ReviewerAgent** — determines whether code satisfies specification and quality requirements

### Phase D: Debugger & Analyst (2-3 sessions)
8. **DebuggerAgent** — root-cause analysis, uses diagnostics + git history to trace bugs
9. **AnalystAgent** — requirements/specification agent ("What exactly are we supposed to build?")

### Phase E: Non-Coding Capability Layer (multi-session, long-term)
10. **Observe capability** — screen, active_window, clipboard, running_apps, filesystem_changes
11. **Computer interaction** — keyboard, mouse, window management
12. **Personal productivity** — calendar, tasks, notes, reminders
13. **Connector/plugin framework** — extensible external service integration
14. **Data tools** — calculator, CSV, JSON, SQL, data analyzer, chart

## What Should NOT Change

- The 5-step agent loop (ADR-5) and workspace feedback bar — these are the differentiator
- The agent-centric routing (ADR-8) — tasks → agents → tools, not tasks → tools → agents
- The iteration limit + wall-clock cap (Session 31-32)
- The check-before-acting safety workflow (Session 32)
- The delegate tool for agent-to-agent collaboration (ADR-8 Phase 3)
