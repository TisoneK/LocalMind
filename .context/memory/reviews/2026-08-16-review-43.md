## Root cause found
`backend/src/adapters/openai_compat.py`, `_add_provider_params` (~line 687):
```python
if self._provider_key == "zai":
    payload["thinking"] = {"type": "disabled"}
```
We **disable GLM's thinking on every z.ai call.** The comment justifies it by "breaks the **ThinkingDispatcher's** 10s timeout" — but **that dispatcher was deleted in Session 239** (legacy intent system). The justification is obsolete; we're crippling a reasoning model for a component that no longer exists.

Contrast:
- Copilot (thinking ON) → GLM reasons → full agentic output.
- Our harness (thinking OFF) → GLM emits ~28 tokens, a terse half-sentence, stops.

Sessions 249 (me) and 252 (Buffy) both mislabeled the terse output as "weak model / free tier budget." That was wrong. Session 252's baseline re-run only proved the ADR-40 tool changes didn't cause the truncation — not that the model is the cause.

## Why it's not a one-line flip
GLM streams many reasoning tokens before the answer; on the z.ai free tier (~0.48 tok/s) that hits `PER_CALL_TIMEOUT_SECS = 45.0` (`backend/src/core/agent/constants.py:64`) → naive re-enable could truncate mid-*thinking*. The plumbing to display reasoning already exists: `_extract_content_and_reasoning` (~line 523) splits `reasoning_content` from `content`; reasoning streams to `StreamChunk.thinking` → ThinkingBlock (~lines 1260/1583/1622/1790). So re-enabling is safe UX-wise; the work is budgeting thinking + making the timeout thinking-aware + keeping the fail-fast for a model that only thinks.
