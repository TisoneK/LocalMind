# Review 51 — todo_write: agent-driven live UI todo checklist (Session 274)

**Agent:** Claude Code (claude-opus-4-8) · **Platform:** macOS (local) · **Core:** 0.5.0
**Commit (product):** `506f958` — `feat(agent): todo_write — agent-driven live UI todo checklist (ADR-43)`

## Trigger
User, on the tools work: "the todos are not live on the ui by the agent, it cant
set them, update nor mark them." Framed within "tools are helpers, not agents —
like web_search: just run and return."

## Diagnosis (grounded, live-reproduced)
Two disconnected systems:
1. **UI Todos** (frontend `TodoList` + `todo_created`/`todo_completed` SSE) were a
   PASSIVE projection of the LLM's parsed plan (loop.py:782) — emitted only for
   plan-required intents, not controllable by the agent.
2. **Subgoal scratchpad** (`add_subgoal`/`update_subgoal`/`create_plan`) — the
   agent *could* call these, but they're a private contextvar registry that emits
   NO todo events, and they're long-tail (behind `describe_tool`, undiscovered by
   a weak model).

**Live-reproduced:** a task literally asking for a 3-step plan emitted ZERO todo
events (agent ran `shell` twice, answered). The panel stays empty for real work.

## Fix
A first-class **`todo_write`** core tool — the agent's direct control surface. It
writes the FULL checklist (`todos:[{text,status}]`, status pending|in_progress|
completed|blocked); the loop's `_emit_todo_write_events` turns the result into the
`todo_cleared` + `todo_created` obs events the SSE bridge and frontend ALREADY
render (full replace, mirroring the plan-todo emission). Pure fast helper: parse,
normalize, return — the loop owns emission (tools can't reach the ObsCollector
across the `asyncio.wait_for` boundary, same constraint as `describe_tool`).

Wiring touched: `Intent.TODO_WRITE` + registration; `CORE_TOOL_NAMES` +
`AGENT_ALLOWED_TOOLS` + core-local/web intent scopes (universal, like `skill`);
`_extract_tool_input` json.dumps branch; `status` carried through the chat.py
bridge (frontend `normalizeTodo` already applied it — no frontend change); prompt
nudge to maintain the checklist on multi-step tasks.

## The bug the first live trace caught
`_extract_tool_input` had no `todo_write` branch, so the fallback stringified the
`todos` array as a **Python repr (single quotes)** → invalid JSON → the tool's
`json.loads` failed with validation_error on every call. Fixed with a `json.dumps`
branch (the find_path/edit_file pattern) + an `ast.literal_eval` fallback in the
tool as defense in depth. This is why the live-verify mattered — unit tests passed
while the real agent path was broken.

## Verification
- **Live (z.ai/glm-4.5-flash):** agent called `todo_write`, **0 validation
  errors**; `todo_created` events flowed with correct shape and status progressed
  `pending → in_progress` live (create + update proven end-to-end).
- Full backend suite **1870 pass** (4 pre-existing env-gated shell fails); **+10
  new tests** (tool normalization + loop emission); ruff clean. Test count pins
  updated for the intentional +1 core tool (CORE 14→15, TOOL_DEFINITIONS 30→31);
  `todo_write` added to goal-interpreter + selection meta-tool exclusions; SHELL
  scoping guard relaxed 0.60→0.62 (a universal tool added to both scope and full
  set raises the ratio; still ~38% saving).

## Honest limit / owed
The weak model demonstrated create + `in_progress` update live but did not mark a
step `completed` before answering in that run — prompt follow-through, not a
mechanism gap (the completed→SSE path is unit-tested and uses the same bridge
plan-todos rely on). A stronger model, or a task with a clearer completion beat,
should exercise the mark-complete live. No frontend code changed — it already
threaded `status`; a visual check of the panel in the real app is still worth doing.

## Relates to
ADR-43 (tools = helpers; todo_write is the fast single-purpose helper the user
described). Supersedes the plan-only passive todo projection as the agent's todo
control. The still-open ADR-43 tools work is B-2026-08-16-5 (L2 steering + L3
redundant read-back).
