## Implementation

Added `_post_loop_synthesis_from_evidence()` to `core/agent/loop.py` and wired it into the empty-response fallthrough path (the path that fires AFTER the B-2026-08-18-11 reasoning rescue fails or doesn't fire).

**Trigger conditions (all must hold):**
1. At least one tool ran this turn (`trace.steps` has a `tool_name`).
2. The `observation_log` is non-empty (there's evidence to synthesize from).
3. The B-2026-08-18-11 synthesis-from-reasoning rescue already ran and returned empty (or didn't fire because there was no reasoning buffer).

**Behavior:** calls `_force_final_answer(framing="final")` with the full `observation_log` + thinking OFF (plain synthesis, not the tool loop). If the synthesis returns ≥ 20 chars, yields it as the final answer. If it returns empty/trivial or raises, yields nothing — the caller falls through to the existing empty-message fallback.

**Guards:**
- No tools ran → skip (no evidence; the empty-message fallback is honest).
- `observation_log` empty → skip (nothing to synthesize).
- Synthesis < 20 chars → skip (too trivial).
- Synthesis raises → caught, yields nothing (defensive).
- Does NOT count against the recovery budget — it's a single final attempt, not a retry.

Emits a `post_loop_synthesis` obs event for observability.

## Key finding: the post-loop synthesis is a backstop, not the primary path

The live traces revealed that the B-2026-08-18-11 synthesis-from-reasoning rescue (Session 298) is the PRIMARY path that fires when the recovery cap is hit. It produces a real answer from the reasoning buffer + observation log. My new `_post_loop_synthesis_from_evidence` is a **backstop** that fires ONLY when:
- The reasoning rescue didn't fire (no reasoning buffer on the final empty iteration), OR
- The reasoning rescue fired but returned empty.

This is the correct layering — the two rescues are complementary:
- **B-2026-08-18-11 (existing):** fires on empty-WITH-reasoning. Uses reasoning buffer + observation log. Counts against the recovery budget (it's part of the empty-response handling).
- **B-2026-08-20-7 (new):** fires on empty-final-text-WITH-tool-evidence but NO reasoning. Uses observation log only. Does NOT count against the recovery budget (it's a post-loop safety net).

## Separate issue surfaced (not fixed this session)

The Trace 2 final answer reveals a **tool-capability hallucination**: the model claimed "The shell tool's available actions (check_disk, check_internet, find_files, ...) do not include a direct hostname command" — but `shell` DOES accept arbitrary `command` strings including `hostname`. The model had just successfully called `shell(hostname)` on iter=3, but then on iter=5 called it with a JSON-wrapped form that failed, and the synthesis concluded the tool can't do it. This is a weak-model reasoning failure, not a harness defect — but it suggests the shell tool's error message (when given a JSON-wrapped command) could be more helpful by suggesting "pass the command as a plain string, not JSON." Backlogged as B-2026-08-20-9.
