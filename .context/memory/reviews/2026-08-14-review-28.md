# Review — Session 223: parent-first realtime workspace contract

## Scope

This was a context/research session only. No product files were modified. The
user's target is to make LocalMind behave as one visible agent at work rather
than a chat response plus tool output:

`understand → acknowledge → plan → act → observe evidence → verify → synthesize`

The review reconciles that target with ADR-8, ADR-17, ADR-18, ADR-30, ADR-31,
ADR-32, and ADR-33.

## Code-verified findings

### 1. Initialization is model-owned, but it starts too late

ADR-33 is implemented: `AgentRuntime` sends a lifecycle status and then
retrieves memory, prepares attachments, builds the full context, and only then
constructs `ParentAgent`/`AgentLoop`. The loop's initialization call is typed
(`direct | clarify | execute`) and therefore fixes the old prompt-specific
routing architecture, but the user-visible model-owned thinker is still behind
context preparation. The first status is transport acknowledgement, not a
model-generated understanding.

The current initialization prompt also enumerates the available tools and
buffers the JSON decision before the UI can render its public acknowledgement,
plan, or next action. This explains the observed silence/black-box behavior even
though a real LLM call exists.

### 2. The UI has two competing execution narratives

The left Actions tab already receives live tool calls, but `ChatMessage` also
renders `ToolSteps` in the transcript. The right panel defaults to `Observe`,
which renders the old `Agent Pipeline` (`Intent Classify → Context Build →
Agent Initialize → Tool Select → Generate → Execute`). The right panel also has
an `Agents` tab, but no event activates it when a parent run starts. Thus the
same work is split between chat, Actions, Observe, Terminal, and Agents rather
than being represented by one live agent workspace.

`AgentWorkspace` currently renders parent/child runs and tool counts, but not
the public initialization decision, plan nodes, evidence observations,
verification/replan phases, or the parent synthesis boundary. It is a useful
foundation, not yet the authoritative live surface.

### 3. Tool results cross the presentation boundary too early

The SSE bridge forwards tool-call/status and terminal output events to the
frontend, which is correct for live evidence. However, the chat-side tool-step
surface makes tool results look like the assistant's answer, and the runtime
contract is not explicit enough about the distinction between:

- evidence visible in an Actions/Terminal/Agent node;
- the tool result returned to the parent model as context;
- the final user-facing answer emitted by the parent after evaluation.

The parent runtime does pass results back through the loop, and it persists the
parent response. The architectural/UI fix is therefore a boundary and reducer
contract, not another tool patch: tools may publish evidence events, but only
parent synthesis may populate assistant final-answer content.

### 4. Intent and Observe are stale product concepts

The parent owns the request decision per ADR-33, yet the UI still exposes
`Intent Classification`, `currentIntent`, intent SSE events, and the pipeline
stage named `intent_classify`. ADR-8 already says classification by task type,
not tool, and ADR-22 says dispatcher output is a hint rather than a directive.
The user's instruction is stronger: intent must no longer be a product-facing
routing concept. Compatibility `Intent` values may remain temporarily at
internal seams, but new UI, routing, and lifecycle design must not depend on
or resurrect them.

The backend stage clock and stored telemetry are still useful measurements, but
their presentation belongs inside agent nodes or a compact run-details view,
not a separate Observe pipeline panel.

### 5. The chat shell still contains obsolete surfaces

Electron's `BrowserWindow` uses default native chrome: there is no `frame`,
`titleBarStyle`, or custom drag-region configuration in `electron/main.js`.
The current product therefore has a default title bar. The left sidebar still
renders the `Autonomous work` objective section, while the normal turn already
has Actions and Todos. That label is confusing for the requested interactive
turn model. Objective runtime/API behavior should not be deleted as part of UI
cleanup without a separate lifecycle decision; the visible section can be
retired or moved to a dedicated background-work surface.

### 6. Prompt size and latency are coupled architectural constraints

ADR-17 measured an approximately 9K static floor per old agent call and
identified 3–5 serial model calls as the main latency cause. Later ADR-33
removed the old direct runtime branch but introduced a model-owned
initialization call. The next design must not add a large second prompt:
initialization should use a compact thinker contract (short public fields,
compact capability names, no full JSON tool schemas), and execution should load
only the selected agent/capability tool contract. A remote/free provider cannot
be guaranteed to return a complete answer in under five seconds, so the honest
SLO is perceived responsiveness: immediate acknowledgement, initialization
start quickly, and first public understanding/next-action update within five
seconds when the provider is available.

## Architectural direction

ADR-34 records the unified contract:

1. One parent-owned initialization decision remains the sole request
   interpretation boundary; no prompt-specific regex routing and no new intent
   classifier.
2. Transport sends a minimal acknowledgement immediately, then the fast
   thinker emits a bounded public understanding/next action. Private
   chain-of-thought remains private.
3. Tool results return to the parent as evidence/context. The frontend receives
   live evidence in Agent/Actions/Terminal nodes, but final chat content comes
   only from parent synthesis.
4. Agents becomes the primary live workspace and auto-activates when a run is
   initialized. Agent nodes own phases, todos, tools, child runs, observations,
   verification, replan, and final synthesis state.
5. Observe's redundant pipeline UI is removed. Backend stage timing remains
   telemetry and is rendered dynamically in the relevant agent node/details.
6. Product-facing intent labels, badges, SSE routing events, and intent-stage
   visualization are retired. Internal compatibility fields may remain only
   while migration is staged and must not regain routing authority.
7. The default Electron title bar and the visible `Autonomous work` section
   are separate shell-cleanup items; they are recorded, not implemented here.
8. Prompt budgets are explicit: compact initialization prompt first, selected
   execution contract second, no duplicate full tool catalog on every call.

## Priority order for implementation sessions

- P0: event/state contract and parent bootstrap ordering (ack → thinker →
  decision → Agent Workspace activation), with a live regression matrix.
- P1: Agent Workspace reducer/nodes and move tool detail out of chat; enforce
  parent-synthesis-only assistant content.
- P2: remove Observe/pipeline and intent UI, migrate stage telemetry into nodes,
  remove the Autonomous work label, and implement title-bar shell cleanup.
- P3: compact prompt budgets and fast-model/profile routing, followed by real
  provider smoke tests measuring first acknowledgement, first public thinker
  event, initialization decision, first action, and final synthesis.

## Risks and non-goals

- Do not expose raw provider chain-of-thought. “Visible thinker” means concise
  public understanding, acknowledgement, plan, and current action.
- Do not promise a complete remote-provider answer under five seconds; measure
  and optimize time-to-first-feedback and time-to-first-decision.
- Do not delete objective persistence/API in this UI session; decide separately
  whether background objectives remain a product feature.
- Do not reintroduce a dispatcher/intent classifier to implement the fast path.
