### Phase B — Greeting + capability ✅

**Issue (Minor):** the "Hi" turn took 8.6s. That's the z.ai API latency (8370ms LLM call), not the harness — but a real user expects a greeting in <2s. The turn-init parallelism (Session 312) is working (the gap before the LLM call is <1s); the bottleneck is the provider.

### Phase C — Simple tool task ✅ (with issues)

- **C1 "What is the hostname?"** → "I'll get the hostname of this machine for you." (46 chars, 27s). The model produced a **prose preamble** ("I'll get the hostname...") and the loop treated it as the final answer — the `MiniMax XML detected in initial buffer` path fired, then `finished iter=1`. **The model did NOT actually call the shell tool.** This is the B-2026-08-20-6 prose-commitment pattern — the detector I shipped in Session 307 should have fired, but it didn't (the MiniMax XML interception path took over first).
- **C2 "List the files in /tmp"** → 878-char real answer listing actual files (LICENSE, README.md, boot-timeline.log, tectonic, data-gym-cache/, etc.). 67s total, 3 iterations: iter=1 (MiniMax XML), iter=2 (empty after reasoning, recovery 1/3), iter=3 (shell `ls -la /tmp` executed ✅). The model DID run the tool and synthesized a real answer from the output.

**Plus:** C2 is a real success — the model ran `shell(ls -la /tmp)`, got the output, and synthesized a clean structured answer. The recovery path (empty-reasoning → nudge → tool call) works.

**Issue (High):** C1 is a real failure — the model committed to calling shell but produced prose instead. The answer "I'll get the hostname of this machine for you." is NOT an answer; it's a preamble. The user gets a non-answer. The B-2026-08-20-6 prose-commitment detector didn't fire because the MiniMax XML interception path (which fires at the initial-buffer stage) consumed the response first. **The two paths conflict** — MiniMax XML interception treats the prose as a completed turn before the prose-commitment detector (at the acceptance gate) gets a chance to nudge.

**Issue (Medium):** the model emitted MiniMax-style XML tool-call markup even for a simple "Hi" (the `MiniMax XML detected in initial buffer during Phase 2 — re-checking` log line fired on B1, B2, B3, C1). This is a z.ai/glm-4.5-flash quirk — it sometimes wraps tool calls in XML instead of using the native tool_calls API. The interception works (the XML is parsed + executed), but it adds an iteration of overhead.

## Summary of findings

### Plus points ✅

1. **Boot is fast and clean** — parent-kernel ready in ~3s, health endpoint surfaces parent_ready correctly.
2. **Conversational turns work well** — "Hi" / "What can you do?" / "Like what?" all produced substantive, structured answers in one iteration with no unnecessary tool calls. The warm kernel + generic direct boundary (ADR-51) are working.
3. **Thinking streams in real-time** — the `thinking_token` SSE events stream as the model reasons, so the user sees progress (not a dead spinner).
4. **Tool execution works end-to-end** — C2 (list /tmp) ran `shell(ls -la /tmp)`, got real output, and synthesized a clean structured answer. The recovery path (empty-reasoning → nudge → tool call) works.
5. **Session persistence is solid** — sessions, messages, and parent_sessions all survive a backend restart. The DB layer is correctly wired.
6. **Observability is correctly surfaced** — `/api/observability/{sid}` returns the parent_session_turn_count and summary.
7. **Turn-init parallelism works** — the gap between "parent running" and "LLM call start" is <1s (Session 312's optimization is live).

### Issues by severity

#### High

- **H1: Prose-preamble non-answer (C1).** The model produced "I'll get the hostname of this machine for you." as the final answer instead of actually calling shell. The B-2026-08-20-6 prose-commitment detector didn't fire because the MiniMax XML interception path (initial-buffer stage) treated the prose as a completed turn first. **The two recovery paths conflict.** Fix direction: the MiniMax XML interception should check whether the prose contains a tool-action commitment before accepting it as final; if it does, route to the prose-commitment nudge instead. Backlog: B-2026-08-20-10.

#### Medium

- **M1: Poor error surfacing on 429.** When z.ai rate-limits, the user sees an empty answer bubble with no explanation. The 429 is in the log, but the SSE `token` content is empty. Fix direction: when the adapter exhausts retries on a 429, emit a user-facing error message ("The model provider is rate-limiting requests. Please wait a moment and try again.") instead of an empty stream. Backlog: B-2026-08-20-11.
- **M2: Recall accuracy after restart.** The model said the first question was "Like what?" when it was actually "Hi". The persistence is correct (the messages are in the DB in the right order); the model misread the order. This is a weak-model reasoning limitation — the recent_tail preserves verbatim text, but the model's synthesis from it is imperfect. No harness fix; document as a known weak-model behavior.
- **M3: MiniMax XML on every turn.** The `MiniMax XML detected in initial buffer during Phase 2 — re-checking` log fired on B1, B2, B3, C1 — the model emits XML tool-call markup even for simple conversational turns. The interception works, but it adds an iteration of overhead and indicates the model isn't using the native tool_calls API reliably. This is a z.ai/glm-4.5-flash quirk; not fixable from the harness, but worth documenting.

#### Low

- **L1: Latency on simple turns.** "Hi" took 8.6s; "What can you do?" took 14.8s. The turn-init is <1s; the rest is the z.ai API. A faster provider (Zen, Cerebras, local Ollama) is the only lever. Not a harness issue.
- **L2: Embedding failure when Ollama is unavailable.** The vector store tries to connect to Ollama for embeddings; when Ollama isn't running (as in this sandbox), memory facts don't get stored. The `[embed] Failed: All connection attempts failed` warning is logged. This is graceful (the turn proceeds without memory facts), but it means the memory system is effectively disabled when Ollama is down. Fix direction: allow a cloud embedding provider as a fallback (or document that memory requires Ollama). Backlog: B-2026-08-20-12.
- **L3: No session-creation API.** `POST /api/sessions` returns 405 (Method Not Allowed). Sessions are only created implicitly via `/api/chat`. This is fine for the frontend (which always sends a chat message to create a session), but a programmatic client can't pre-create a session. Low priority — the implicit creation is the designed flow.
