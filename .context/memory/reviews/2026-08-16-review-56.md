## What the code actually does (verified)

### 1. The "rate-limited" fallback exists but is NOT unconditional

`backend/src/core/agent/loop.py:3000-3045` — the degraded-evidence path fires
only when ALL of these hold:

- the stream carried an error (`has_error` / error markers in the buffer), AND
- `_has_successful_evidence` = at least one tool step with `tool_failed=False`, AND
- `normalize_error()` classified the error as `source == "model_provider"` AND `retryable`, AND
- the **"rate-limited" phrasing specifically** requires `code == "rate_limit"` (otherwise it says "the provider failed the final synthesis call").

So the message is gated on a genuine provider-error normalization, not a
blind guess. For Cerebras, the tokens/min cap on the post-tool synthesis call
is a **documented, recurring behavior** (ai-models.md S251/S252/S276: "cerebras
still rate-limits the post-tool synthesis (tokens/min cap)"). In the disk-space
repro the tool succeeded first, so the next model call hitting a real 429 is
the *expected* outcome — **the transcript's "nothing was rate-limited" claim
is likely wrong**; the provider probably did 429 the follow-up call. The
external AI was inferring from UI text without seeing the SSE error payload.

### 2. The sharper finding VERIFIES: correct synthesis is discarded

The genuinely actionable bug in the transcript is the second one — "discarded
correct synthesis":

- The Thinker consults once on first evidence (`loop.py:2499-2545`) and streams
  its reasoning live (`thinking=` chunks, visible in the ThinkingBlock).
- Its `_analysis` is appended to `loop_messages` via `_thinker_context_block()`
  — a **loop-local** variable that goes into the next model call.
- When that next call (the final synthesis) fails with a provider error, the
  degraded path calls `_summarize_trace_for_user()` (`loop.py:4739`), which
  lists **tool calls only** — it has no access to `_analysis` (or the streamed
  reasoning). The already-correct answer ("13.55 GB — not enough") is dropped
  from the reply.

So the user sees: correct reasoning in the ThinkingBlock → then "I ran the
tools but couldn't synthesize… (provider rate-limited)" + raw tool evidence.
The headline *contradicts* the evidence below it (tool succeeded) and the
reasoning above it (answer computed). That is the real failure mode, and it is
fixable: **carry the Thinker's analysis (or the captured reasoning) into the
degraded-evidence fallback** so a correct intermediate synthesis becomes the
reply instead of being discarded.

### 3. The shell "flattening" claim is unverified

The transcript's scenario 1 (Kenyan notes) blamed a PowerShell parse error
(`-Path was unexpected at this time`) on "a multi-line command getting
flattened into one line." `backend/src/tools/shell.py` passes the command
string verbatim to `powershell -NoProfile -NonInteractive -Command <cmd>`
(Session 189 routing) — **no newline-flattening code exists in the shell
tool.** The malformed command is model-generated, not tool-mangled. The
transcript's own UI capture shows the command display truncated at `-eq "C:`
(display cut, not necessarily the real command), so display truncation vs a
broken model command can't be distinguished from the transcript alone. Marked
unverified; needs the raw tool_input to confirm.
