## Implementation

Added `prose_commits_to_tool_action(text)` to `core/agent/loop.py` and wired it into `_acceptance_gate_at_final_answer`. The detector fires when ALL of:
1. `is_parent=True` (parent-scoped only — non-parent paths unchanged).
2. No tool ran this run (`not any(step.tool_name for step in trace.steps)` — the completion-floor path owns the "tool ran and failed" case).
3. The prose contains BOTH a commitment phrase ("let me describe", "I'll use", "I need to call"...) AND a tool-name mention (shell, describe_tool, file_read...). The conjunction is required — a phrase alone is too easy to false-trigger on legitimate prose ("let me use an analogy"), and a tool name alone is common in capability questions.
4. A `[TOOL COMMITMENT]` nudge hasn't already been injected this turn (one-shot guard — the model had its chance).
5. `iteration + 1 < effective_max_iter` (don't nudge at the cap).

When all conditions hold, the gate injects ONE `[TOOL COMMITMENT]` re-prompt into `loop_messages` and returns `("", False)` — the loop continues for another iteration. If the model still doesn't emit a tool_call, the one-shot guard prevents a second nudge and the turn falls through to the honest-stop path.

## Key finding: the detector is a backstop, not the primary path

The live traces revealed that LocalMind already has a `_is_tool_talk` detector (`core/agent/text_tools.py:399`) that catches the prose-preamble pattern at the **initial-buffer stage** — BEFORE the acceptance gate. It fires on patterns like `r"i (will|would|need to|am going to) (use|call|invoke|run) (the )?(\w+) tool"` and `r"let me (use|call|invoke|run) (the )?(\w+) tool"`, suppresses the leaked text, and retries (up to `_MAX_TOOL_TALK_RECOVERIES = 2`).

My `prose_commits_to_tool_action` detector at the acceptance gate is a **backstop** for phrases the existing regex misses:
- The existing regex's verb alternation is `(use|call|invoke|run)` — it does NOT include "describe."
- The Session 306 trace had "Let me first describe the shell tool" — this would NOT match the existing regex (because "describe" isn't in the verb list AND "first" sits between "me" and "describe").
- My detector catches this via the phrase `"let me first"` + tool-name `"shell"`.

So the two detectors are complementary:
- **`_is_tool_talk` (existing):** fires early (initial buffer), suppresses text, retries. Broad coverage of use/call/invoke/run verbs.
- **`prose_commits_to_tool_action` (new):** fires late (acceptance gate), only when no tool ran this run. Catches "describe" and other phrases not in the existing regex. One-shot bounded.
