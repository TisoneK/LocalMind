# Session 230 Review — Thought process ≠ final answer (ADR-34 init fix)

- **Date:** 2026-08-15 | **Agent:** Claude Code / claude-opus-4-8 | **Platform:** macOS 15 (local) | **Core:** 0.5.0
- **Feature:** bugfix on adr-34-realtime-workspace (Super Z, Sessions 224-229)
- **Target (user, solo):** The "Thought process" showed the final answer
  verbatim — the same ~one-paragraph blob rendered as thinking, as the reply,
  and again in the Agent Workspace cards.

## Root cause
For direct-mode (quick) replies, the streaming initializer surfaced the
model's `response` (the answer) as the "understanding"/thinker line:
- `init_stream.render_understanding` fell back to `response[:160]` when no
  `objective` was present.
- the `loop.py` init producer triggered "understanding" on `response` for
  direct mode.
That thinker line is rendered in BOTH the chat ThinkingBlock and the Agent
Workspace lightbulb card → the answer appeared as the thought process (and
twice more). It also exposed the answer as chain-of-thought, which ADR-34
explicitly forbids.

## Fix
The thinker now surfaces the model's `objective` (its reasoning about what
the user wants) or a clarifying question — never `response`. Two surgical
edits (`init_stream.py`, `loop.py`) + updated init-streaming regression
asserting the answer never leaks into the thinker.

## Not a bug on our side
The direct answer streams verbatim as one chunk (`loop.py:1482`), so
whitespace is preserved. The "no spaces / poor formatting" seen with the
free `deepseek-v4-flash-free` model is its raw `response` output, not a
join/render defect — filed as a follow-up needing a real-model repro.
