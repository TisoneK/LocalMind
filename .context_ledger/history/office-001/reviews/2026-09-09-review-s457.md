## What shipped

1. **`search_tool_results` tool** (`backend/src/tools/search_tool_results.py`,
   `Intent.SEARCH_TOOL_RESULTS`): session-scoped hybrid search over the stored
   index, JSON-or-plain-string args, honest no-match = success, bounded output
   (kept < 5 KB so a retrieval result never re-indexes itself). LONG_TAIL /
   on-demand — its schema loads into the native tool surface only on turns that
   actually store a large result.
2. **`_carry_observation`** (`loop.py`): at **dispatch**, a >5 KB tool result
   is indexed in full and carried as a bounded head + `id=<result_id>` pointer;
   ≤5 KB returns each call site's existing carried form (fallback). Applied at
   all three carried surfaces (parallel-batch, single-tool, seed). Behavior
   changes ONLY for large results.
3. **Storage hardening** (`storage/tool_result_index.py`): `index_result` made
   idempotent (its documented-but-unimplemented intent); added a `result_id`
   search filter; added a process-wide singleton shared by loop + tool.

## Key design decision — where to hook

The first attempt hooked at the pre-send compaction site. It never fired:
tool results are bounded to `OBS_LOG_MAX_CHARS` (2000) by `_truncate_observation`
**before** they enter `loop_messages`, so nothing is >5 KB there and the tail is
already discarded. The full payload only exists at **dispatch** — that is the
only correct place to index. (Logged in `inefficiencies/log.md`.)

A second issue, caught in the same live run and fixed before shipping: the
retrieval tool's own output exceeded 5 KB and got re-indexed, so the model
chased nested pointers into its own searches. Fixed by exempting
`search_tool_results` from indexing by name and capping its output under 5 KB.

## Live verification (mandatory bar)

Provider **bankofai / qwen3.8-flash** (free; deepseek-v4-flash is paid,
balance 0), isolated port 8765 + scratch `LOCALMIND_HOME`. Same task both runs:
fetch the full HTTP/1.1 spec (RFC 2616, ~400 KB) and answer what 404 means.

| | BEFORE (origin/main) | AFTER (this change) |
|---|---|---|
| large result carried | full ~10,035 chars inline | ~2,150-char head + pointer (**~79% less**) |
| indexed | no (`trc_chunks` absent) | yes (3 chunks, `web_fetch-3e2f06e…`) |
| retrieval | n/a | model called `search_tool_results` with the exact `result_id`, retrieved the buried **§10.4.5** definition |
| answer | correct | correct (identical) |
| iterations / prompt tok | 2 / 5,776 | 5 / 6,050 |

The AFTER answer was produced from *retrieved* content (§10.4.5 sits far past
the 2000-char head), proving the pointer→search→answer path end to end.

**Honest trade-off:** for a single buried-fact question the retrieval
round-trips cost slightly more cumulative tokens than carrying the whole result
once. The win is on multi-result research turns — where the old behavior
ballooned context and lost older results to lossy truncation, and the new
behavior keeps a bounded footprint with everything retrievable.
