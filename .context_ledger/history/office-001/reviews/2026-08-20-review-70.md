## Root cause

The active `AgentRuntime` sent every user turn into the parent initializer. That initializer is a meta-call: it classifies the tier and writes the direct answer inside a constrained JSON envelope. On the real GLM stream this cost roughly 930 prompt tokens and 11–20 seconds, and produced broad repetitive prose for a capability question and its follow-up. The existing generic direct-chat helpers were present but were not used by the live runtime.

The root issue was the missing **generic direct-conversation boundary**, not the wording "What can you do?". The capability-specific deterministic branch from Session 300 was removed. Direct responses now use the normal adapter chat call with recent history and one model-agnostic prompt; tool-bearing, attachment, and ambiguous turns remain on the parent loop.

## Product change

- Removed `is_capability_question()` and the deterministic capability catalog/examples.
- Runtime conversational turns now call the generic `conversational_response()` helper with recent conversation context.
- The direct prompt explicitly resolves short follow-ups from context and asks for concrete examples when requested, without naming capability phrases.
- History-backed opener-less follow-ups are structurally constrained to question-shaped forms (including natural "Like what" / "And why" forms), preventing action requests from skipping the parent tool loop.
- Preserved fast-path lifecycle events, all five stage-timing events, persistence, metrics, and workspace artifacts.

## Honest limits

The direct boundary still uses a conservative structural classifier to keep evidence-requiring requests out of a no-tool chat call. This is not a phrase-to-answer map and has no capability-specific response logic. Provider latency remains real GLM generation latency (~10–16 seconds); the fix removes the redundant meta-classification and large prompt cost rather than claiming zero latency for model-backed conversation.
