## Executive Summary

The "Tools execution failure" bug the user reported was NOT caused by model
overload, context window overflow, or silent failure in the agent loop. It
was caused by **two adapter bugs in `backend/src/adapters/openai_compat.py`**,
both confirmed with raw API calls against the user's exact model
(`deepseek-v4-flash-free` via Zen):

1. **HTTP 400 on trailing `tool` role** — DeepSeek rejects requests where
   the last message is a `tool` role. The agent loop sends this exact format
   after every tool execution.
2. **Phase 1 detection drops tool_call deltas during long reasoning streams** —
   DeepSeek produces 80+ reasoning chunks before the tool_call delta. Phase 1
   broke at chunk 15, fell through to Phase 2b, which silently dropped the
   tool_call deltas (it only handles content/reasoning).

Both bugs are fixed in commit `d09327c`. The user's diagnosis was 100% correct.

## How the root cause was found

### Step 1: Test the synthesis call in isolation

Script `scripts/repro_zen_silent_failure.py` called `adapter.chat()` (what
`_force_final_answer` sends) with the user's exact 4-tool context. Result:
**the model returned a perfect 677-char synthesis in 7.65s.** The synthesis
call works fine. The bug is NOT in `_force_final_answer`.

### Step 2: Test `chat_with_tools` with the full message history

Script `scripts/test_chat_with_tools.py` called `adapter.chat_with_tools()`
with the full 4-tool message history (what the agent loop sends after every
tool execution). Result: **HTTP 400 "Upstream request failed".** The API
rejected the request.

### Step 3: Isolate the 400 error

Script `scripts/isolate_400_error.py` tested different message formats
against the raw API. Found that messages with `tool_calls` + `tool` role
→ 400, but simple messages → 200.

### Step 4: Confirm the exact rule

Script `scripts/confirm_root_cause.py` tested every combination of
trailing message role:

| Last message role | Result |
|---|---|
| `tool` | ❌ 400 |
| `user` | ✅ 200 |
| `assistant` (no tool_calls) | ❌ 400 |
| `assistant`+tool_calls (no tool followup) | ❌ 400 |

**Root cause #1 confirmed**: DeepSeek-v4-flash-free requires that the
message list ends with a `user` role message. The agent loop sends
messages ending with `tool` role after every tool execution → 400.

### Step 5: Fix Bug 1, re-test, find Bug 2

After implementing Fix 1 (append synthetic `user` message when last is
`tool` role), re-tested `chat_with_tools`. No more 400 — but the model
returned ZERO text (just `[DONE]`). Enabled DEBUG logging and found
Phase 1 detection was breaking at `chunks_read >= 15` during the
reasoning phase.

### Step 6: Parse the raw SSE stream

Parsed the raw streaming response: DeepSeek produces **80 reasoning
chunks, then 27 tool_call delta chunks, then `finish_reason=tool_calls`**.
The tool_call was at chunk 81 — well past the Phase 1 break at 15.

Phase 2b (`_stream_from_http`) only handles `content` and `reasoning_content`
— NOT `tool_calls`. So the 27 tool_call deltas were silently dropped. The
model's tool call was lost; user saw empty output.

**Root cause #2 confirmed**: Phase 1 detection gives up too early on
reasoning-only streams, falling through to Phase 2b which drops tool_calls.

## Fixes Applied

### Fix 1: Synthetic user message after trailing `tool` role

**File:** `backend/src/adapters/openai_compat.py` (`chat_with_tools` method)

When the last message is a `tool` role, append a synthetic `user` message:
"Based on the tool result above, continue. Either call another tool if
needed, or provide your final answer to the user."

This is harmless for providers that don't require it (the model just sees
an extra instruction) and necessary for providers that do (DeepSeek, and
possibly others).

### Fix 2: Phase 1 keeps reading during reasoning-only streams

**File:** `backend/src/adapters/openai_compat.py` (`chat_with_tools` method,
Phase 1 detection block)

Changed the break condition: only break out of Phase 1 if we've seen
actual `content` (not just reasoning). Reasoning-only chunks mean the
model is still thinking and hasn't decided between text vs tool call yet.
Added a hard cap of 500 chunks to prevent infinite looping if the model
streams reasoning forever.

### Fix 3 (intermediate, still valuable): Evidence-based fallback messages

**File:** `backend/src/core/agent/loop.py` + `backend/src/core/engine/_pipeline.py`

Commit `f316904` (before the root cause was found) revised the fallback
messages to surface actual tool inputs/outputs from `trace.steps` instead
of guessing "overload." This fix is still valuable — honest evidence >
speculation — but it was treating the symptom, not the cause. The root
cause fix (`d09327c`) is what actually makes the user's scenario work.

## Regression Tests

5 new tests in `tests/adapters/test_zen_deepseek_fixes.py`:

1. `test_synthetic_user_appended_when_last_message_is_tool_role` — verifies
   Fix 1: synthetic user message is appended when last message is `tool` role.
2. `test_no_synthetic_user_when_last_message_is_user` — verifies Fix 1
   doesn't fire when last message is already `user`.
3. `test_synthetic_user_appended_after_each_tool_role` — verifies only ONE
   synthetic user is appended (not after each tool role).
4. `test_phase1_does_not_break_on_reasoning_only` — verifies Fix 2: Phase 1
   keeps reading during 20 reasoning chunks and detects the tool_call at
   chunk 21.
5. `test_phase1_breaks_on_content_after_15_chunks` — verifies Fix 2 doesn't
   break the normal text-detection path.

Baseline held: 395 tests pass (390 + 5 new), 0 serious ruff bugs.

## Lessons Learned

1. **When a fallback message GUESSES at a cause, treat the guess as a
   hypothesis to test, not a diagnosis to ship.** My "overload" guess was
   plausible-sounding but unverified. The user correctly pushed back. The
   real-model test took 10 minutes and found the actual bug in 2 API calls.
   Should have done this BEFORE writing the fallback message, not after.

2. **The user's instinct to check the filesystem was right.** "Did the
   directory get created, did git init happen, does hello.py exist?" is
   the correct diagnostic question. The fallback message was blaming the
   model when the real issue was the API rejecting the request format.

3. **Real-model testing is irreplaceable.** Mocked adapter tests gave
   false confidence — the bugs were in the adapter's handling of real SSE
   streams, which mocks can't reproduce. The user's offer to provide an
   API key was the move that cracked it.
