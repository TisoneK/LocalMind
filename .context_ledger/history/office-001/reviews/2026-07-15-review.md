# Session 11 — Git Identity Fix (same date, same chat session)

> **Review date:** 2026-07-15 (continuation — third session in the same chat)
> **Reviewer:** Super Z (GLM-5.2, Z.ai — per Session 5 correction; not re-confirmed)

> **Scope:** Fix incorrect git authorship on the 3 commits from Sessions 9–10.

## Correction — stale SHA references

The Session 9 and Session 10 sections above (and the Session 9/10 entries in `agents/sessions.md`) reference these commit SHAs:
- `1ada84f` (Session 9 sync)
- `ddd4a98` (core 0.2.0 migration)
- `970f72a` (Session 10 log)

**These SHAs are stale.** Session 11 rewrote the authorship of all 3 commits (they were shipped as `Z User <z@container>` — the sandbox default — instead of `Tisone Kironget <tisonkironget@gmail.com>`). The new SHAs are:

| Old SHA (stale) | New SHA (current) | Session | Tree hash (unchanged) |
|---|---|---|---|
| `1ada84f` | `e3cdd40` | 9 | `c0695cb` |
| `ddd4a98` | `fe120dc` | 10 | `c0422da` |
| `970f72a` | `b581d30` | 10 | `2a15f18` |

Tree hashes are identical old↔new for all 3 pairs — the rewrite changed only authorship, not content. Per append-only rules, the Session 9/10 entries and the Session 9/10 sections above are left as written; this mapping is the authoritative correction.

## What happened

The cloud edition's Step 0-C.2 explicitly says: `git config user.name "<GIT_NAME>" && git config user.email "<GIT_EMAIL>"` after clone. I skipped this on both Session 9 and Session 10. The Z.ai sandbox has a global git identity (`Z User <z@container>`), so commits succeeded silently with the wrong author. Every prior session (1–8) correctly committed as `Tisone Kironget <tisonkironget@gmail.com>` — the discrepancy was visible in `git log`.

The user caught it: "You did not set my git info even before pushing."

## Fix applied

1. Set local git config: `git config --local user.name "Tisone Kironget"` + `git config --local user.email "tisonkironget@gmail.com"`.
2. Rebased the 3 commits with corrected authorship: `git rebase 55e702a --exec 'git commit --amend --reset-author --no-edit'`.
3. Verified tree content unchanged (tree hashes match old↔new for all 3 pairs).
4. Force-pushed with `--force-with-lease`: `970f72a...b581d30 main -> main (forced update)`.

No new content commits. The repo content is byte-identical to before; only the author/committer fields on 3 commits changed.

## Root cause

Agent error, not a protocol gap. The protocol explicitly says to set git config. I treated the clone as "done" once the repo was on disk, without completing the identity step. The sandbox's silent global identity masked the omission — commits didn't fail, they just went out under the wrong name.

## Prevention

Reinforced in `memory/user/preferences.md` (Workflow section): "Set local git config before first commit on cloud/sandbox — identity must match `memory/user/identity.md`; the sandbox default is never the user's identity." Future cloud sessions must run `git config --local user.name/email` as part of Step 0-C.2, immediately after clone and before any commit.
