## Session 310 — raise empty-reasoning recovery cap for parent turns

### Implementation

Live traces on z.ai/glm-4.5-flash (Sessions 306-308) showed the model frequently hits `empty-response-after-reasoning` on multiple iterations of a single tool-bearing turn. The cap of 2 (`_MAX_EMPTY_REASONING_RECOVERIES`) was exhausted before the model could complete the turn, leaving only the post-loop synthesis (B-2026-08-20-7) to produce an answer.

Introduced `_MAX_EMPTY_REASONING_RECOVERIES_PARENT = 3`, distinct from the non-parent `_MAX_EMPTY_REASONING_RECOVERIES = 2`. The parent path (which sets `_parent_native_turn` via `skip_planning=True` + `agent_config.name == "parent"`) now gets one extra recovery attempt.

The recovery-cap check at `loop.py:3766` now reads:
```python
_empty_reasoning_cap = (
    _MAX_EMPTY_REASONING_RECOVERIES_PARENT
    if _parent_native_turn
    else _MAX_EMPTY_REASONING_RECOVERIES
)
if _streamed_reasoning and trace.empty_reasoning_recoveries < _empty_reasoning_cap:
    ...
```

### Why 3 and not higher

- The post-loop synthesis (B-2026-08-20-7) remains the final safety net, so even if the raised cap is hit, the user still gets a synthesized answer from evidence.
- Each recovery attempt costs a full LLM round-trip (~30s on z.ai free tier). 3 recoveries = ~90s of recovery overhead, which is already a lot for a single turn.
- The hard upper bound (3) + the iteration cap (`MAX_ITERATIONS`) + the post-loop synthesis together bound the turn — no infinite-loop risk.
- The non-parent cap stays at 2 (don't loosen legacy/child paths).

- **3 new tests:** `tests/core/test_parent_recovery_cap.py` — cap value assertion (3 > 2), parent path gets ≥ 4 `chat_with_tools` calls (1 tool + 3 recoveries), non-parent path still caps at 2 (unchanged).
- **1035 broad regression tests pass** (was 1010; +25 across sessions 308-310). The existing `test_second_empty_after_reasoning_still_fails_fast` (ADR-41) still passes — it uses the non-parent path, so the cap stays at 2 for it.
