# Review — z.ai/GLM-4.5-flash: incomplete output + input-token bloat (Session 249)

**Agent:** Claude Code / claude-opus-4-8 · **Date:** 2026-08-16 · **Provider under test:** z.ai `glm-4.5-flash` (free)

## Task
User reported three issues with the free z.ai/GLM-4.5-flash provider, prioritized:
1. Incomplete output {HIGH} — final answers truncated ("Found 2,670 markdown files… Here", cut off).
2. Too much input token {MEDIUM} — ~18.7k prompt tokens on a simple file-listing turn.
3. Latency {LOW} — 62s at 0.48 tok/s.

## Method
Live traces on an isolated backend (`LOCALMIND_PORT=8765` + isolated `LOCALMIND_HOME` copy of the user's settings, adapter forced to `zai`; port 8000 = user's app never touched; API-key values never read/printed). Reproduced "Show me md files in /Users/bao/Code". Instrumented the adapter to log `finish_reason` and payload byte-sizes, then removed the instrumentation.

## Findings (measured)
- **Input is ~14–17k tokens PER CALL, even for "hi".** Payload breakdown (live): system message **41,812 chars** (incl a **10,936-char tool-text injection**) + native `tools` param **25,399 chars** (all **30** tools) ≈ **17,380 tokens**. The tool catalog was sent **THREE times**: the native `tools` param, a text injection into the system prompt, and the tool list already inside the agent system prompt.
- **Incomplete output is the MODEL, not a code cap.** The provider's own usage reports exactly **28 completion tokens** ("Found 703 markdown (.md) files in /Users/bao", cut mid-path). Ruled out:
  - An explicit `max_tokens=4096` did NOT change it (so no low provider default / no cap of ours).
  - Removing 2.7k of input did NOT lengthen the output (so not a simple total-token budget — the user's reasonable "input swallows output" hypothesis was not supported by the reduction test).
  - The stream was fully consumed at 28 tokens (`is_stream_consumed`), so nothing was dropped by us in this case.
  - Output is deterministic across runs → the weak model genuinely produces a terse, slightly-wrong summary and stops (`finish_reason=stop`). Contributing: thinking is disabled for z.ai (terse), evidence truncated to 1008 chars, synthesis prompt doesn't demand completeness.
- **Latency** is the model itself (0.48 tok/s on the free tier) — not code-fixable; input reduction only helps marginally.

## Fixes shipped (`a5c0a0b`)
1. **Removed the redundant tool-text injection** — verified live: input 16,763 → 14,098 tokens/call (~2.7k saved), tool-calling intact. (Issue #2, partial.)
2. **Fixed a latent stream-tail drop** — `_stream_from_http` gated "read the rest of the stream" on `not phase1_done`, but Phase 1 sets that True on a MID-STREAM text break (chunks_read≥15) where the stream is NOT consumed → tail dropped for models that stream in many small chunks. Now guarded on `is_stream_consumed` alone; removed dead `phase1_done`. Did NOT change GLM's current 28-token answer, but prevents truncation once answers grow.

Full backend suite **1,764 passed** (4 pre-existing env-gated `test_shell.py`).

## Not done / next (need a provider with quota — z.ai free rate-limited during testing)
- **Bigger input cut (B-2026-08-15-14):** scope tools to the intent (the "analyze" intent sent all 30 tools) and stop duplicating the tool list inside the system prompt. The `tools` param alone is ~6.3k tokens/call.
- **Issue #1 real mitigation:** a synthesis-prompt nudge for a complete, structured answer (count + first N files), and/or richer (less-truncated) evidence for listing tasks. Must be live-verified — GLM's terseness is a model property, so this is coaxing, not a guaranteed fix.

No product regression claimed for issue #1 — it is a model-quality limitation, honestly reported.
