## Root cause addressed

ADR-52 phase 1 (Session 302) shipped the boot-owned `ParentKernel` and removed the per-turn JSON initializer, but left two gaps explicit in the ADR's "open implementation questions":

1. **No rolling session memory.** The runtime assembled each turn's prompt from `history[-8:]` with per-message truncation. Long conversations would either bloat linearly (if the window were raised) or silently lose earlier turns (at the fixed cap). There was no compacted summary layer.
2. **No distinct parent readiness signal.** `/api/health` exposed `engine_ready` (a single boolean set after `startup()` returns) but not the parent kernel's distinct ready/degraded state. A boot where the cloud provider was unreachable would still report `engine_ready: true`; the frontend had no way to surface "parent degraded, lazy retry pending."

## Product implementation

### 1. `ParentSession` — per-chat rolling summary (new: `core/parent_session.py`)

A dataclass holding:
- `rolling_summary: str` — compacted prose for older turns (one line per folded turn: `User asked: ... | did <tool> | answered: ...`).
- `recent_tail: list[dict]` — the exact last N (default 6) user/assistant pairs, preserved verbatim. This is the "verified evidence + user wording" layer that's never compacted away.
- `turn_count: int` — durable counter that survives backend restart.

**Compaction policy:** when `recent_tail` exceeds `RECENT_TAIL_MAX=6` pairs, the oldest pair is folded into `rolling_summary` as a one-line entry. When the summary exceeds `SUMMARY_MAX_CHARS=4000` (≈1000 tokens), the oldest third is dropped (most recent entries are at the end of the summary string, so trimming from the start preserves them).

**Tool-action fold:** each summary entry optionally includes a `tool_summary` line (e.g. `shell(ls -la)`) so the summary records what the agent *did*, not just what it said. Bounded to the first 3 distinct successful tools per turn.

**Prompt injection:** `to_prompt_section()` returns a system message bracketed by `[Conversation so far — compacted summary...]` / `[End of summary. The messages that follow are the most recent turns, verbatim.]`, or `None` on turn 1 (no summary yet).

### 2. Persistence (migration 009 + `storage/db.py`)

New `parent_sessions` table (session_id PK → sessions ON DELETE CASCADE, rolling_summary TEXT, recent_tail TEXT JSON, turn_count INTEGER, updated_at REAL). Added `SessionStore.save_parent_session()` and `get_parent_session()`. The migration is applied via the existing `_apply_migrations` path; no manual ALTER needed.

### 3. Runtime integration (`core/agent_runtime.py`)

At turn start (`_process_unlocked`):
- Load the ParentSession from the store (survives restart).
- Inject its `to_prompt_section()` as a system message BEFORE the recent tail.

After turn completion (only when the response is a real answer, not the empty-response fallback):
- Fold (user_message, response_text, tool_summary) into the session.
- Persist via `save_parent_session()`.

`_summarize_tool_actions(collector)` is a new module-level helper that extracts the first 3 distinct successful tool calls from the ObsCollector for the summary entry.

### 4. Readiness telemetry

`AgentRuntime._ensure_parent_kernel` now queues readiness transitions on `self._pending_readiness`:
- `parent_ready` — first successful build, or any rebuild that wasn't a recovery.
- `parent_degraded` — build where provider warmup failed (carries `reason`).
- `parent_recovered` — rebuild that succeeds after a prior degraded state.

`drain_pending_readiness()` returns and clears the queue. `_process_unlocked` drains it onto the turn's ObsCollector immediately after `agent_runtime_start`, so the frontend SSE sees `parent_ready` / `parent_degraded` / `parent_recovered` as ordinary `obs_event` payloads on the first turn after boot or a settings change.

Two new read-only properties on `AgentRuntime`:
- `parent_ready: bool` — True when the boot kernel is built and not degraded.
- `parent_degraded_reason: str` — the warmup failure string (empty when ready).

### 5. Surface in `/api/health` and `/api/observability`

`HealthResponse` gains `parent_ready: bool` and `parent_degraded_reason: str`. Overall `status` is now `"ok"` only when provider is reachable AND engine_ready AND parent_ready; a degraded parent reports `"degraded"` while still serving requests (lazy retry).

`ObservabilityData` gains `parent_session_summary: Optional[str]` and `parent_session_turn_count: int`. Both endpoints load from the persisted store so the values survive a backend restart.

### Compaction behavior (unit-tested, not live-verified)

The 8-turn live compaction trace exceeded the tool-call time budget (z.ai free model is ~15s/turn × 8 turns). Compaction is covered by **13 unit tests** in `tests/core/test_parent_session.py`:
- `test_tail_compacts_when_over_limit` — 9 turns → tail capped at 6, oldest 3 folded into summary.
- `test_summary_includes_tool_action` — tool_summary appears in the folded entry.
- `test_summary_trims_at_char_cap` — 150 turns → summary bounded at SUMMARY_MAX_CHARS, oldest entries dropped, most recent preserved.
- `test_persistence_via_session_store` — save → load round-trip.
- `test_persistence_survives_reconnect` — fresh SessionStore on same DB file reads the saved row.

### Honest limitations

- **Compaction not live-verified on the real model.** The unit tests prove the data shape and persistence; the live trace proved the turn-counter persistence path. A future session with a faster provider (or a longer time budget) should send 8+ turns to confirm the rolling summary appears in `/api/observability` on a real model.
- **`provider_usage` empty on turn 4.** The captured `turn_complete` event had no `provider_usage` field (z.ai doesn't always return streaming usage headers). The runtime's existing fallback estimates tokens locally; this is not a regression.
- **No frontend changes.** The new SSE events and `/api/health` fields are surfaced on the wire, but the React frontend's StatusBar doesn't yet render `parent_ready` / `parent_degraded_reason` distinctly from `engine_ready`. That's a separate UX slice (backlogged).
