# Session 31 Review — 2026-07-27

## Executive Summary

User reported "Tools execution failure" — the agent ran shell + file_write
tool calls (visible in UI as `[shell] Create Project Phill directory...` and
`[file_write] Write Hello World Python script...`), showed a "Running command"
spinner for 52.8s, then surfaced a uselessly generic fallback message:

> "I wasn't able to complete that request. The tool may have failed or
> returned no useful output. Please try rephrasing your request."

The root cause was NOT the shell tool itself — the original `re` conditional
import bug from `docs/shell_tool_fix_analysis.md` was already fixed in a prior
session (verified: `import re` is at module top, line 38 of `shell.py`;
`SYSTEM = platform.system()` resolves once at module level, line 54).

The remaining bug was the **silent-failure fallback path** in the engine +
agent loop. When the model returned an empty stream after tool execution
(common with free-tier models — overload, context overflow, or all output
filtered as system-leak XML), the engine emitted a generic message that:

1. Told the user nothing about what tools actually ran
2. Mis-attributed the failure to the user's phrasing (almost never the cause)
3. Gave no concrete next step beyond "rephrase"

This session closes that gap with three coordinated fixes plus 11 regression
tests.

## Findings

### Finding 1 — Critical: Silent-failure fallback message was uselessly generic

**Location:** `backend/src/core/engine/_pipeline.py:2471-2476`

**Symptom (user report):**
> "I wasn't able to complete that request. The tool may have failed or
> returned no useful output. Please try rephrasing your request."

**Root cause:** When `full_response_chunks` was empty after the agent loop
ran (the model produced zero text chunks, or all chunks were filtered out
as system-leak XML), the engine emitted a hardcoded generic message that:

- Gave no indication of what tools actually ran
- Mis-attributed the failure to the user's phrasing — the real cause is
  almost always free-tier model overload or context window overflow
- Suggested "rephrasing" as the only remedy, which is rarely the right fix

**Impact:** Every user who hit a free-tier model overload after tool
execution saw this message and had no idea what to do. The UI showed
tools running, then a useless error — making the system feel broken
rather than transparent.

### Finding 2 — Critical: `_force_final_answer` silently returned nothing on empty model stream

**Location:** `backend/src/core/agent/loop.py:2974` (pre-fix)

**Root cause:** The function's `try/except` only caught exceptions. If
`active_adapter.chat()` yielded ZERO chunks (empty stream — common with
free-tier models), the function returned without yielding anything. The
engine then saw an empty `full_response_chunks` and fell through to
Finding 1's generic message.

The exception fallback at the `except` block did yield a meaningful
message (with the observation log) — but ONLY on exception, not on
empty stream.

### Finding 3 — High: Streaming path didn't check for empty `full_text` after the model stream ended

**Location:** `backend/src/core/agent/loop.py:~2527` (pre-fix)

**Root cause:** When the model produced chunks but ALL of them were
filtered out by `_filter_system_leaks` (e.g., the model output was
entirely `<action>...</action>` XML, or MiniMax `<invoke>` XML), the
`full_text` variable was empty after the streaming for-loop. The loop
then returned at line 2540 without yielding any text, and the engine
fell through to Finding 1's generic message.

## Fixes Applied

### Fix 1 — `_force_final_answer` tracks empty model streams

**File:** `backend/src/core/agent/loop.py`

Added `_any_text_yielded` tracking. After the `try/except`, if no
non-empty text was yielded, yield a fallback that:

- If `observation_log` has content (failed tools logged): surface the
  observation log so the user sees what failed
- If `observation_log` is empty (all tools succeeded, model just
  couldn't synthesize): suggest switching models / one step at a time

Also added a `return` after the exception fallback (was missing —
without it, the new empty-stream check would fire AFTER the exception
fallback, yielding two messages).

### Fix 2 — Streaming path yields trace summary on empty `full_text`

**File:** `backend/src/core/agent/loop.py`

After the streaming for-loop ends, if `full_text.strip()` is empty,
yield a new `_summarize_trace_for_user(trace, observation_log)` fallback
that lists every tool that ran (with status: ok/failed, plus an error
snippet for failures). This means even when the model output is entirely
filtered out, the user STILL sees what the agent did on their behalf.

### Fix 3 — Engine fallback is now intent-aware

**File:** `backend/src/core/engine/_pipeline.py`

Replaced the generic "Please try rephrasing your request" message with
intent-aware text that:

- Names the intent that was being handled (`_intent_label`)
- States the real cause (free-tier model overload, not user phrasing)
- Suggests three concrete next steps: switch model, one step at a time,
  re-run (transient overload is common)

This is the last-resort fallback — it should rarely fire now that Fixes
1 and 2 ensure the loop always yields text on the silent-failure path.

### Fix 4 — 11 regression tests

**File:** `tests/e2e/test_tool_execution_failure.py` (new)

Four test classes:

1. `TestForceFinalAnswerEmptyStream` — verifies Fix 1 (3 tests)
2. `TestSummarizeTraceForUser` — verifies the trace-summary helper (5 tests)
3. `TestEngineFallbackMessage` — verifies Fix 3 (2 tests, source-level)
4. `TestEndToEndSilentFailureScenario` — simulates the user's exact case
   (model returns empty stream after shell + file_write) and asserts the
   user gets a meaningful message, not the generic one
