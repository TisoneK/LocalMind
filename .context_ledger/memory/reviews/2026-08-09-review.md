## Executive Summary

The reviewer conversation is **substantially correct**. Its two headline concerns — (1) a conversational query that should be near-instant takes ~40s, and (2) the Observe panel cannot tell you where that time went — are both confirmed as genuine, code-level gaps. Three of its smaller suggestions (per-message latency, prompt/completion token split, consistent latency units) are confirmed as real UI gaps, one with a caveat (the split already exists in the bottom bar; "prompt: 0" is partially addressed by Sessions 64–65 and needs a live re-verification).

The broken-bullet/`**` markdown observation is a **model-output quality issue, not a UI rendering bug** — ReactMarkdown + remark-gfm render standard markdown correctly; a stray unclosed `**` renders literally. No fix should ship without a real-model reproduction (per the Session 31/33 flaw-log rule).

**Root latency diagnosis (verified):** "What can you do?" is not caught by the trivial-input short-circuit (only greetings/thanks/farewells/yes-no/acks) or by signal detection, so it pays **two sequential LLM calls** — the ThinkingDispatcher capability-inference call (big JSON-schema prompt, `DISPATCHER_TIMEOUT_SECS=30`, runs on the main model) and then the actual chat generation call (full `context_builder` prompt). With a slow free-tier provider each call is 10–20s; they add up to ~40s. `maybe_compress_history()` is a potential *third* sequential LLM call on long conversations. The UI's 8.06 tok/s figure is averaged over total elapsed time including the dispatcher call, so it understates real generation speed.

**Biggest observability gap (verified):** The pipeline stage display in the Observe panel is a **frontend heuristic** — five invented stage names ("Intent Classify → Context Build → Tool Select → Generate → Execute") with statuses inferred from a handful of observation fields, not real per-stage timings. No stage timing is emitted by the backend (only per-stage *events* like `dispatcher_complete`, `memory_retrieved` — their `latency_ms` values are emitted but never displayed). This is exactly why the reviewer saw "Tool Select orange/running" on a completed no-tool turn and why nobody can say where the 39.9s went without grepping server logs.

**Findings:** 2 High, 6 Medium, 6 Low/Nice-to-have. No Critical (nothing destructive). No fixes applied this session — the user's brief was analysis + recording + ADRs. Three ADRs (10–12) and eleven backlog items were filed.

## Findings

### HIGH

#### H1 — Conversational queries pay 2–3 sequential LLM calls; this is the 39.9s root cause
- **Where:** `backend/src/core/engine/_pipeline.py` (trivial check ~L845, dispatcher ~L1008, DIRECT chat ~L1077–1296, `maybe_compress_history` ~L1142); `backend/src/core/thinking_dispatcher.py` (LLM capability inference ~L380–520, `DISPATCHER_TIMEOUT_SECS=30`).
- **Evidence:** For a non-trivial conversational query ("What can you do?" = 4 words, but matches no trivial pattern, no signal, no follow-up):
  1. `ThinkingDispatcher.dispatch()` → one LLM call with the large `_CAPABILITY_INFERENCE_SYSTEM` JSON-schema prompt, `temperature=0.2`, on the **main model** (`best_model_for`; the `ollama_model_fast` shortcut only applies to local Ollama).
  2. `_execution_mode == DIRECT` path → `context_builder.build()` (full system prompt + memory + history) → **second LLM call** (`active_adapter.chat`).
  3. `maybe_compress_history()` runs before generation — another **potential third LLM call** when history approaches the context window.
- **Impact:** Two provider round-trips for a question that needs one; on a slow free tier this is ~40s total. This confirms the reviewer's hypothesis #1 (multiple sequential model calls). The model itself is not the bottleneck (as the user correctly argued) — the *pipeline's* redundant calls are.
- **Note:** `DISPATCHER_HIGH_CONFIDENCE_SKIP` (0.6) only skips orchestrator+planning for `AGENT_INTENTS` (`_pipeline.py` ~L1900); it does **not** help CHAT/DIRECT turns, which still pay the dispatcher call before the skip logic is even reachable.
- **Recommendation:** Deterministic pre-classification must catch obvious conversational questions before the dispatcher (extend `trivial_input.py` with a "conversational question" category: interrogatives + no tool keywords), and/or the client-intent header fast path must fire automatically for simple queries (server support exists — see L6). See ADR-10, B-2026-08-09-1, B-2026-08-09-6.

#### H2 — No per-stage timing instrumentation: the Observe panel cannot show where latency goes
- **Where:** `backend/src/core/engine/_pipeline.py` (per-stage `latency_ms` is computed and emitted — `dispatcher_complete`, `memory_retrieved`, `turn_complete` — but never aggregated per stage or surfaced); `frontend/src/components/panels/ObservabilityTab.tsx` (pipeline steps are a hardcoded heuristic).
- **Evidence:** The frontend's five pipeline steps are invented names with inferred statuses:
  ```ts
  const pipelineSteps = [
    { name: 'Intent Classify', status: hasIntent ? 'done' : 'pending' },
    { name: 'Context Build',  status: hasIntent ? (hasToolCall || hasCompletion ? 'done' : 'running') : 'pending' },
    { name: 'Tool Select',    status: hasToolCall ? 'done' : hasIntent ? 'running' : 'pending' },
    { name: 'Generate',       status: hasCompletion ? 'done' : hasToolCall ? 'running' : 'pending' },
    { name: 'Execute',        status: hasCompletion ? 'done' : 'pending' },
  ];
  ```
  No backend stage named "Context Build", "Tool Select", or "Execute" exists. `dispatcher_complete.latency_ms` and `memory_retrieved.latency_ms` are emitted into obs events but **no frontend code reads them**.
- **Impact:** The reviewer's exact ask — "log a timestamp at start/end of each stage and see which stage eats the 10s+" — is impossible from the UI today. Also makes the panel actively misleading (see M1).
- **Recommendation:** Emit a structured `stage_timing` obs event per turn (per-stage name + duration_ms) and render it in the Observe panel (collapsed per-stage breakdown). See ADR-11, B-2026-08-09-2.

### MEDIUM

#### M1 — Observe pipeline status is heuristically misleading (reviewer's "Tool Select orange" observation)
- **Where:** `ObservabilityTab.tsx` pipelineSteps (above).
- **Verified:** On a completed no-tool turn (`hasIntent=true, hasToolCall=false, hasCompletion=true`): Tool Select → **'running' (orange forever)**; Execute → 'done' even though nothing executed. Exactly what the reviewer saw. The stage names also imply a pipeline shape LocalMind doesn't have.
- **Recommendation:** Either replace with real backend stage data (ADR-11) or relabel/remove; at minimum "Tool Select" must be able to resolve to "skipped/not needed" after completion.

#### M2 — Trivial-input turns emit no `turn_complete`; the observability fallback is session-agnostic
- **Where:** `_pipeline.py` trivial short-circuit ~L845–865 (emits only `trivial_short_circuit` / `trivial_short_circuit_done`, no `intent_classified`, no `turn_complete`, no `_store_observation`); `backend/src/api/routes/observability.py` fallback ~L94–105 (`engine._metrics.get_all_metrics()` picks **any** intent with requests — not scoped to the session).
- **Verified:** For "Hi", the stream emits no obs data the Observe panel understands, and the polled `/api/observability/{session}` falls back to a **global aggregate** — the panel can show a different session's intent/latency for a greeting turn.
- **Impact:** The fastest turns (the ones the reviewer wants to verify) show the least/wrong observability. This also explains part of the "—" states.
- **Recommendation:** Emit a proper `turn_complete` on the trivial path (it already computes `elapsed_secs`); make the fallback per-session. See B-2026-08-09-5.

#### M3 — Latency units inconsistent across surfaces; raw unlabeled ms in the Observe panel
- **Where:** `ObservabilityTab.tsx` MetricBar (`displayValue = safeValue > 0 ? safeValue : '—'` → shows e.g. `39853`, no unit) with a **hardcoded `max={10000}`** (so >10s always renders a full bar); `PerformanceMetrics.tsx` bottom bar already formats adaptively (`latency >= 1000 ? s : ms`).
- **Verified:** Exactly the reviewer's complaint — bottom bar "39.9s", side panel "39853" raw. The `max=10000` also visually saturates for any slow turn.
- **Recommendation:** Shared formatter (sub-second → ms, ≥1s → one-decimal s) everywhere; remove the hardcoded max or derive from data. See B-2026-08-09-4.

#### M4 — No per-message latency/token display; metrics are last-turn-global only
- **Where:** `frontend/src/components/chat/ChatMessage.tsx` (only `message.timestamp` shown; no metrics field on `ChatMessage` in `types/index.ts`); engine `_last_observation` is a single dict per session (last turn wins); `_store_observation` **merges** fields across turns (`_pipeline.py` ~L483).
- **Verified:** The reviewer's per-message chip idea is a genuine feature gap. There is no per-turn metrics history anywhere.
- **Recommendation:** Add optional per-message latency/token metadata (populated at turn_complete via a new SSE field on the done event, or a `metrics` field on persisted messages). See ADR-12, B-2026-08-09-3.

#### M5 — Global `_process_lock` serializes all engine requests engine-wide
- **Where:** `_pipeline.py` `process()` ~L772 (`async with self._process_lock:` wraps the entire stream).
- **Verified:** While one request streams (up to 39.9s+), any other request (second client, ObjectiveRuntime turn, CLI) **blocks on the lock** until the first generator is exhausted. The main UI masks this (single-stream guard in `send()`), but objectives/CLI/multi-window do not.
- **Impact:** A plausible contributor to the user's "Hi took >10s" in a busy session, and a latent reliability issue for the objective runtime.
- **Recommendation:** Investigate making the engine request-scoped or locking per-session/per-intent instead of globally. See B-2026-08-09-9.

#### M6 — "Vector Store Hits" is mislabeled and conflates 0 with missing data
- **Where:** `ObservabilityTab.tsx` (`{memoryHits > 0 ? memoryHits : '—'}` under the label "Vector Store Hits"); backend populates it from `memory_hits=len(memory_facts)` — the count of memory facts injected into the prompt, **not** vector-store query hits.
- **Verified:** The value is memory-facts count; there is no actual vector-hit metric surfaced. "—" renders for both "no data yet" and "legitimately 0 facts" (fresh session), so the reviewer's "instrumentation not wired" guess is half-right: the field *is* wired (Sessions 64–65), but the label/display make it unreadable.
- **Recommendation:** Rename to "Memory Facts", and distinguish 0 from missing (e.g., "—" only when the session truly has no observation). See B-2026-08-09-8.

### LOW / NICE-TO-HAVE

#### L5 — Conflicting dispatcher timeout constants

- **Recommendation:** Reconcile (single source; comment why 30 was chosen — GLM/Z.ai was 18s typical). See B-2026-08-09-11.

#### L6 — Client pre-classification exists but never fires automatically
- **Where:** `client.ts` streamChat ~L326 (`if (toolHint)` sets `X-LocalMind-Intent`); `_pipeline.py` ~L951 (`if client_intent and client_confidence >= 0.9` → skips dispatcher, `fast_path=True`); `useLocalMind.ts` ~L987 passes `tool` (only set by explicit UI tool buttons).
- **Verified:** The server fast path and the client plumbing both exist — but nothing classifies ordinary messages client-side, so the dispatcher always runs for non-trivial input. The perf plan's §3.3 "pre-classification at client" is only half-built.
- **Recommendation:** Fold into the H1 fast-path work (extend `trivial_input` server-side first; client hint as the follow-on). See B-2026-08-09-6.

#### N1 — tok/s is averaged over total elapsed time including dispatcher/planning
- **Where:** `useLocalMind.ts` token handler (~L400: `estimatedCompletionTokens / (liveElapsed / 1000)`), `metrics.py` `record_streaming_complete` (total tokens / full request).
- **Verified:** For multi-call turns the displayed tok/s understates generation speed (the reviewer's 8.06 tok/s includes the dispatcher's dead time). Per-stage timing (H2) naturally fixes this.

#### N2 — Observe panel shows only the latest observation (no history), by design
- Not a bug, but the reviewer's "correlate by eye/timestamp" pain is real. The per-message chip (M4) is the proper fix.
