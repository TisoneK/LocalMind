# Review — Session 222: model-owned parent initialization

## Executive summary

The previous addressed-greeting fix was a symptom patch. It preserved a deterministic
runtime branch that decided whether a request was conversational before the parent
agent existed. That contradicted LocalMind's intended architecture: the parent must
first understand the request and decide whether to answer, clarify, or act.

Session 222 removes that live shortcut and introduces a typed parent initialization
contract. Every user turn now crosses `AgentRuntime → ParentAgent → AgentLoop`; the
parent's first model call returns `direct`, `clarify`, or `execute`. Execute decisions
produce a bounded acknowledgement/plan and then continue through the existing
parent-owned tool/observation/verification loop. Direct decisions use the same first
call's answer and do not make a second execution call.

## Discovery

- `AgentRuntime` was still importing `trivial_input` and returning before `ParentAgent`
  for greetings and conversational questions.
- `AgentLoop` had a planning call for substantive intents, but it was free-form plan
  text, not a general request interpretation contract; it could not own direct versus
  clarify versus execute decisions.
- The runtime passed `Intent.ANALYZE` as a parent compatibility hint, while the
  parent had the full allowed tool contract. The new initialization prompt exposes
  the full available tool surface and treats any old routing hint as non-authoritative.
- Existing SSE status, todo, tool, terminal, and final-token bridges were sufficient;
  only the backend decision boundary and the Observe stage list needed changes.

## Implementation

- Added `core/agent/initialization.py` with:
  - `InitializationDecision` (`direct`, `clarify`, `execute`)
  - bounded JSON prompt contract and robust fenced/noisy JSON parsing
  - fail-open execute fallback when a provider emits malformed initialization text
  - acknowledgement, objective, plan steps, tool names, and success criteria fields
- Changed the live parent loop to run initialization before tool execution, emit
  `agent_initialization_*`, visible statuses, todos, and a real `agent_initialize`
  stage timing event.
- Removed `AgentRuntime._process_direct_conversation()` and the live
  `is_trivial_input` / `is_conversational_question` routing branch. The legacy module
  remains only as a compatibility utility and is explicitly documented as unused by
  live request routing.
- Added the `Agent Initialize` stage to the frontend Observe pipeline.
- Replaced the stale changelog claim that greetings use a deterministic zero-call
  boundary with the model-owned initialization behavior.

## Acceptance criteria

- A direct initialization decision produces the user answer and exactly one parent
  initialization provider call; no `chat_with_tools` execution call occurs.
- An execute decision performs initialization first, then makes parent tool-loop calls;
  tool observations remain available to the parent for the next decision.
- A malformed initialization response does not route by regex or silently end the turn;
  it fails open to bounded parent execution.
- Raw initialization JSON/provider reasoning is not emitted as chat content.
- Existing direct, workflow, tool-observation, provider-error, SSE, and UI regressions
  remain green.

## Limitation / follow-up

No live-provider smoke was run because credentials were unavailable. The new contract
reduces architectural misrouting, but provider generation latency remains dependent on
the selected model. A future live smoke should verify that the chosen free model emits
valid initialization JSON quickly and that the UI displays acknowledgement → plan →
action → evidence in real time.
