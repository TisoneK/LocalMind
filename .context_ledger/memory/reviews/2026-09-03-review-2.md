## Approach

Used a subagent (Explore type, Task ID 2-a) to map the current tool schema state + ADR-40 before making changes. The subagent's report:

1. Confirmed ADR-40 is already implemented (16 long-tail tools behind describe_tool; 18 core tools always-present).

This is a good example of multi-agent deployment: the subagent's research-heavy exploration caught a flaw the main agent would have missed if it had applied the audit's literal recommendation.

### ADR-40 guardrail: tool SELECTION verification

The guardrail requires live-verification that tool SELECTION still works (right tool, valid args) on a weak model after the schema cut. Verified on bankofai/qwen3.8-flash:

- **iter 1:** `web_fetch` (python.org) — correct, core tool
- **iter 2:** `web_fetch` (python.org/about) — correct, core tool
- **iter 3:** `web_fetch` (rust-lang.org) — correct, core tool
- **iter 4:** `web_search` (go.dev official description) — correct, core tool
- **iter 5:** final answer produced (`turn outcome=answer recovery=none`)

The model did NOT call `describe_tool` at all — it used the core web tools directly. This is the desired behavior: moving `web_research` to long-tail did NOT break research tasks; the model used `web_fetch` + `web_search` (both core) instead. No hit_limit; same 5 iterations as baseline.

### Note on the first fix-2 run

The first fix-2 run hit the iteration limit (6 iters, hit_limit=True). Initially suspected a regression. Re-running fix-2b succeeded cleanly with 5 iters and a final answer. The hit_limit was VARIANCE (the model took a different path: web_search for exact taglines instead of web_fetch for a 4th URL), NOT a schema-cut regression. Tool selection was correct on BOTH runs (web_fetch + web_search, both core). Logged to `inefficiencies/log.md` (Session 411): when a live-test shows an iteration-count increase, re-run to confirm variance before reverting.
