# Review 55 — As-completed streaming for parallel tool batches (Session 279, B-10)

**Agent:** Claude Code (claude-opus-4-8) · **Platform:** macOS (local) · **Core:** 0.5.0
**Commit (product):** `cf38bc0` — `feat(agent): as-completed streaming for parallel tool batches (B-10)`

## Trigger
ADR / user follow-up: "invoke multiple tool calls and wait for outputs from each
separately … results caught concurrently." The loop already dispatched a parallel
batch concurrently (`asyncio.gather`) but BLOCKED on the whole batch and emitted
all tool_call done-events together — a fast tool's card waited for a slow sibling.

## Change
- Per-task `_dispatch_and_emit` emits each tool's done/failed event AS IT FINISHES;
  `asyncio.as_completed` drives the batch and the loop `yield`s after each so the
  SSE bridge flushes it to the user immediately.
- Model-context assembly (observation_log / trace.steps / tool_messages) rebuilt in
  INPUT order (`_results_by_idx[i]`) so it stays deterministic.
- Latent bug fixed: the old post-gather done-event used `_inp` (the label loop's
  LAST value) → every parallel tool's card showed the wrong args; each event now
  carries its own call's input.

## The finding that matters more than the change
**The user's models don't emit NATIVE parallel tool_calls.** I tried hard to
trigger the `MultiToolCallResult` path live:
- glm-4.5-flash: serialized (one tool per iteration); when asked for "parallel" it
  called the `delegate_parallel` TOOL (with bad args, looped).
- gemini-2.5-flash: same — `describe_tool(delegate_parallel)` → repeated
  `delegate_parallel` calls; independent tasks (calculator + find) were serialized.

So parallelism with these providers happens via the **delegate_parallel tool**, not
native multi-tool-call batches. B-10's native-path improvement is correct but
**rarely activates in practice** with these models. This may reprioritize: if
parallel UX matters, the delegate_parallel path is where it actually happens.

## Verification — HONEST STATUS
- Full suite **1875 pass** (4 pre-existing env-gated shell fails); no regression.
- Stale-args fix: correct by inspection.
- As-completed ORDERING: **NOT live-verified** — the MultiToolCallResult path did
  not activate on either model (see finding). No existing test harness drives the
  parallel loop path (the P5 tests only check the dataclass), and building one is a
  heavy full-loop mock. The change is low-risk (contained to that path). I am not
  claiming "verified" — per system/live-testing.md, unit tests + correctness are
  not the same as a live trace, and I could not get one.
