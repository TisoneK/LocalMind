# Vector memory dimension mismatch — root cause and repair

## What happened

The reported error was `Vector batch write failed: Dimension mismatch for
inserted vector for the "embedding" column. Expected 768 dimensions but
received 1024.` — memory writes were failing at runtime (503s on
`POST /api/memory`, silent drops of the agent's own fact writes) while the
app still started and reported healthy.

The local DB (`C:\Users\tison\LocalMind\localmind.db`) was in a split state:

- `vector_meta.dim` = **1024** (matches `mxbai-embed-large:latest`, the model
  in `settings.json`);
- the sqlite-vec table DDL was `USING vec0(embedding float[**768**])`, frozen
  when the index was first created under a 768-dim model (`nomic-embed-text`,
  no longer pulled);
- 4 facts present, 0 vectors (so nothing was corrupted — the index was empty).

## Root cause

`vector_meta.dim` was treated as the source of truth. sqlite-vec freezes a
vec0 table's dimension at `CREATE` time and `CREATE VIRTUAL TABLE IF NOT
EXISTS` never alters it, so the table's DDL is what an INSERT is actually
checked against. Because the startup probe compared the embedder (1024) only
with the meta row (1024), `_init_db` declared the store ready, left the stale
768 table in place, and every `_persist` batch died at runtime. Nothing
reconciled the two. `scripts/reset_vector_db.py` repeated the same meta-only
comparison and reported "Dims match — no mismatch detected."

Two further defects surfaced while fixing it:

1. `_embed_cached` retried a failed embed request with `settings.ollama_model`
   (the *chat* model). A chat model does not produce a comparable embedding —
   this is a silent path to writing a different space/dimension into a live
   index.
2. `_drop_vector_tables` in the reset script ran `DROP TABLE vector_embeddings`
   on a connection with the sqlite-vec module **not loaded**, inside
   `except Exception: pass`. The drop silently failed, so the subsequent
   `CREATE VIRTUAL TABLE IF NOT EXISTS` kept the old 768-dim table and the
   reset crashed partway through re-embedding. That is why the repair had to
   be run twice.

## What changed

`backend/src/storage/vector.py`

- New `_vec_table_dim(conn)` — parses `float[N]` from the live vec0 table's
  DDL. The table, not the meta row, is the ground truth.
- New `VectorStore._reconcile_vec_dim()` called at startup:
  - table dim == meta dim → unchanged behaviour;
  - empty index with a stale table → rebuild at the embedder's (or recorded)
    dimension, repair `vector_meta.dim`, drop the stale `embed_backend_id`
    (a backend id with no vectors claims a space that no longer exists);
  - populated index → trust the table over the meta row; correct the meta row
    when the probe agrees, otherwise record a real mismatch
    (`_dim_mismatch`) and stay not-ready with reset instructions.
- `_persist` now compares incoming vector lengths with the index dim before
  opening the transaction and refuses the batch with a clear, actionable error
  (previously sqlite-vec rejected it mid-transaction and the message was
  opaque).
- `recall_with_scores` guards query-vector length the same way.
- `_embed_cached` no longer falls back to the chat model; a failed embed
  request logs which model/status failed and returns no vector.
- The recorded-backend space guard now requires at least one stored vector —
  an empty index with facts (the post-reset shape) is no longer blocked.

`scripts/reset_vector_db.py`

- Reads and reports both `vector_meta.dim` and the vec0 table dim, and decides
  on the table dim (the meta row alone can mask a real mismatch).
- A meta-only drift with an otherwise-correct table is reported as
  self-healing at startup rather than triggering a full re-embed.
- `_drop_vector_tables` loads sqlite-vec on its connection and no longer
  swallows the drop error; the rebuild verifies the created DDL matches the
  probed dimension before re-embedding.
- Records `embed_backend_id` for the Ollama backend that re-embedded the
  facts.

`tests/core/test_vector_dim_reconcile.py` — 9 regression tests: stale empty
table rebuilt; empty table without meta adopted and tracked; populated table
trusted over stale meta; populated table + different embedder refused; stale
backend id ignored when the index is empty; runtime width-change refused;
no chat-model fallback; reset script reads the table dim; the drop really
removes the vec0 table.

## Verification

- New tests: 9/9 pass. Existing vector suites
  (`test_vector_embed_fallback.py`, `test_vector_store_busy.py`): 22/22 pass.
- Real DB repaired with the fixed script: 4 facts re-embedded, 0 failed. The
  table is now `float[1024]`, `vector_meta` = 1024, backend id
  `ollama|http://localhost:11434|mxbai-embed-large:latest`, 4 facts / 4
  vectors.
- Live: `npm start` booted, startup memory write succeeded, a manual fact was
  stored and recalled through `POST /api/memory` and `GET /api/memory/search`
  (relevance 0.86), then deleted. No `Dimension mismatch` anywhere in the log.
- Pre-repair backup kept at `C:\Users\tison\LocalMind\localmind.db.bak-20261031`
  (with its `-wal`/`-shm`); safe to delete once the user is satisfied.

## Still open

- `reset_vector_db.py` still probes Ollama only. A cloud-embedder-only setup
  (Ollama unreachable, cloud configured) cannot use the script to rebuild —
  the store itself handles that path, but the repair tool does not. Filed to
  the backlog.
- The startup reconciliation intentionally refuses a *populated* index whose
  table dim disagrees with the active embedder rather than silently
  re-embedding it; that remains a manual reset, by design.

## What to do next

Nothing required for the reported bug. Delete the `.bak-20261031` files when
convenient, and if the embed model is ever changed again, run
`python scripts/reset_vector_db.py --probe-only` first — it now sees the real
index dimension.
