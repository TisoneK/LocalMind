# Review 67 — Session 298: web_search relevance-gated race (Kitengela weather failure)

- **Date:** 2026-08-18
- **Agent:** Claude Code | **Model:** claude-opus-4-8 | **Platform:** macOS (Darwin 24.6, local) | **Core:** 0.8.0
- **Task:** user pasted a live LocalMind transcript (glm-4.5-flash) where "Whats the weather like in Kitengela rn" failed: 3 web searches all "ok", then `empty_response` / "Agent loop failed". Diagnose + fix.

## Root cause (live-proven, not guessed)

The visible `empty_response` was a **symptom**. Ran the actual providers against the exact query:
- **Bing** returned garbage: `current.com` (a fintech), "Electric current — Wikipedia", a Chinese dictionary entry for the **word** "current". It latched onto "current" and ignored "weather Kitengela".
- **DuckDuckGo** returned **correct** results: "7-day weather forecast Kitengela", "Weather for Kitengela, Kenya", Weather Underground, Ventusky…

The race (`web_search.py`) was `asyncio.wait(FIRST_COMPLETED)` — **the fastest provider wins regardless of relevance** (old line ~555, "First provider to return results wins!"). Bing (a fast single scrape) beat DDG's correct results. The model then had no weather data, retried the same search 3× (each "successful" so the same-tool-failure streak never tripped — the tool *succeeded*, the results were just useless), and returned an empty synthesis.

## Fix (`1304a24`)

A **relevance gate** on the race in `backend/src/tools/web_search.py`:
- `_query_content_tokens` — the query's distinctive terms (≥3 chars, minus function/question/temporal-framing words incl. "current/right/now"; so "current weather Kitengela Kenya right now" → `{weather, kitengela, kenya}`).
- `_relevance_coverage` — how many distinct query terms a result set covers.
- `_is_relevant_enough` — near-full coverage required (all terms for <4-term queries, all-but-one for longer). Near-full is deliberate: generic domain words alone must not pass, so a **Los-Angeles** weather page (matches weather/forecast/temperature but not the LOCATION) is rejected for a Kitengela query.
- The race: a provider wins immediately only if it clears the bar; an off-topic-but-fast set is **held as a fallback** while better providers finish; if none clears the bar, the **best-covering** set is returned (never fewer results than before). No latency regression for well-formed queries (a relevant fast provider still wins instantly).

General + model/env-agnostic — no per-topic rules, no provider favoritism.

## Verification

- **LIVE (real network):** all 3 transcript queries now return **DuckDuckGo Kitengela/Kenya weather** instead of Bing junk / LA weather.
- **Unit/integration:** 9 new tests (helpers + a race regression proving relevance beats a faster off-topic provider + best-effort fallback). Full backend suite **1961 passed / 0 failed**; `web_search.py` ruff clean.
- **De-flaked** two existing tests (`test_web_search.py`, `test_chat.py`) that patched only DDG and left Bing hitting the **real network** — now mock all three providers (deterministic).
