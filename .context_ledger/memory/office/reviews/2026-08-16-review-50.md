## 1. The sequence — where we are

Optimization of the agent runtime has proceeded in three deliberate phases, each
building on the last:

1. **Agent (the loop / runtime).** Closed-loop control, three-tier routing
   (ADR-37), token efficiency (ADR-39), prompt caching, error normalization
   (ADR-20/21), the empty-after-reasoning recovery (S256/257/261). The loop that
   *drives* the tools is now stable and cheap.
2. **Thinker (the reasoning backbone).** Built from the ground up as a module
   (ADR-42), made to reason on **gathered evidence** not the raw request, anchored
   on the real user request (S263), and bounded with thinking levels (S262). The
   part that *decides what to do* now reasons genuinely.
3. **Tools (the hands).** ← **WE ARE HERE.** The agent decides well and the loop
   runs cheaply, but the *tools it reaches for* are still uneven: some are lean,
   bounded helpers; others behave like mini-agents that dump unbounded output and
   do open-ended work. This phase makes the tools themselves efficient.

The order matters: you cannot judge tool efficiency until the loop and the
reasoning above it are stable — otherwise you mistake a loop/reasoning cost for a
tool cost (as we did in S262, where 202s of *thinking* was first misread as slow
tools; the shell itself ran in 754ms).

## 2. Two cost axes of a tool — and which is left

Every tool costs the agent twice:

- **INPUT cost** — the tool's *schema* shipped in the model's `tools` param every
  call. **This axis is largely solved** by ADR-40: lean schemas (option B,
  S251) + on-demand long-tail loading via `describe_tool` (option C, S252) cut the
  per-call catalog ~68% (24,230 → 7,851 chars). Diminishing returns remain.
- **RUNTIME cost** — what a tool costs *when it actually runs*:
  - (a) **Output context** — how many tokens its result injects into the loop's
    context for every subsequent turn. **Untouched.**
  - (b) **Latency** — wall-clock the agent waits. Partly bounded (shell has a 20s
    timeout) but not audited across the heavy tools. **Secondary.**

**This research is about the RUNTIME axis, primarily output-context cost.** It is
the sibling of ADR-40, on the other side of the tool call.

## 3. The principle (the user's north star)

> "The tools don't need to take too long since they are helpers of the agent and
> tools — not agents. file_finder is more efficient than raw shell commands."

A tool should be a **bounded, single-purpose helper** that returns a **summary
sized for a model's working memory** — not a raw pipe that dumps arbitrary output,
and not an open-ended explorer that does agent-sized work. When a tool behaves
like an agent (unbounded output, arbitrary scope, its own multi-step logic), it
competes with the agent for context and time instead of serving it.

## 4. Grounded evidence

### 4a. The clearest contrast in the codebase: `shell` vs `find_path`

- **`find_path`** ([find_path.py](../../../backend/src/tools/find_path.py)) returns
  a **catalog**: total match count, folder + extension histograms, and a small
  *page* of paths. "The model sees the catalog summary, never the [raw] walk"
  (module docstring). The true total is always counted so the catalog never lies
  about scale, but the context payload stays bounded regardless of how many files
  match. **This is the shape to generalize.**
- **`shell`** ([shell.py:760](../../../backend/src/tools/shell.py)) returns the
  **entire raw stdout** as its result content — no cap, no summary, no elision
  (`return ToolResult(content=content, …)` where `content` is the full captured
  process output). A `Get-ChildItem` / `ls -R` / `find` / `cat` dump lands whole
  in context and rides along in every following turn.

That single asymmetry is the disease in miniature: one tool is a helper, the other
is a raw pipe. It is also the direct cause of the S262 "context too long" failure
— unbounded reasoning was the trigger, but unbounded shell output was the fuel.

### 4b. Observed inefficiencies in live traces (this program)

| # | Observation (from real traces) | Why it's a tools problem |
|---|---|---|
| 1 | Agent ran `ls ~/Desktop` / `Get-ChildItem` **before a create task** | Nothing to discover — a create task needs `file_write`, not an exploratory listing. The listing then fed the Thinker irrelevant evidence (the `.lnk` shortcuts it had to reason past in S263). |
| 2 | Agent used **`shell` for file discovery** | `find_path` is the bounded, purpose-built discovery helper. Raw `shell` returns unbounded output and invites the model to write brittle OS-specific commands (the PowerShell/`\`-vs-`/` class of bugs). |
| 3 | Agent did a **read-back self-verify** (`file_task`) after `file_write` | The loop **already verifies** the write (`file_write verification passed: expected=… actual=…`). The extra read is a redundant tool call — and on Windows it hit the S264 path bug and cascaded to `empty_response`. |
| 4 | Verbose tool output bloats context | Raw dumps (4a) accumulate across turns; on a free tier with a small context this is what tips a multi-step task into overflow. |

## 5. Tool taxonomy — helper vs agent-like

Classifying the 33 registered tools by *shape* (not usefulness) sharpens where the
work is:

- **Bounded helpers (already the right shape):** `find_path` (catalog),
  `calculator`, `json` / `csv` / `sql` (structured in, structured out),
  `file_write`, `file_task`, `edit_file`, `web_search` (ranked hits),
  `sysinfo`, `installed_programs`.
- **Raw / unbounded (fixable — bound the output):** **`shell`** (raw stdout, the
  top offender), `code_exec` (arbitrary stdout), `web_fetch` (page text can be
  huge), `git` (diffs/logs can be huge), `process_tool`.
- **Agent-like by nature (heavy; the question is *selection* + output bounding, not
  removal):** `browser_agent` (486 LOC, drives a browser), `delegate` /
  `delegate_parallel` / `delegate_inline` (literally spawn sub-agents),
  `best_of_n_edit` (614 LOC, runs N generations). These are legitimately heavy —
  the goal is that the agent picks them only when warranted and that even they
  return bounded observations.

## 6. Optimization levers (research options — not yet decided)

**L1 — Bound every tool's output (highest value, safest).** Give raw-dump tools
the `find_path` treatment: cap the result at ~N tokens with a head/tail + elision
marker ("… 412 more lines"), or a structured summary, and keep the full output
retrievable **on demand** (the `describe_tool`/`skill` load-on-demand precedent).
Start with `shell`; extend to `code_exec`, `web_fetch`, `git`. North star: *no
tool injects more than a small, fixed budget of context by default.*

**L2 — Right-tool steering.** Nudge the agent to the bounded helper: discovery →
`find_path` (not `shell`); "create X" → `file_write` directly (skip the
exploratory listing); structured data → `json`/`csv`/`sql` (not `shell` text
munging). Mechanisms: cheap prompt guardrails in the tool index (ADR-40 already
carries per-tool guardrail prose — extend it), and/or a pre-dispatch hint from the
Thinker (which already reasons about the next step).

**L3 — Eliminate redundant tool calls.** The post-write read-back duplicates the
loop's own verification. Fold the confirmation into the `file_write` result
(already reports verified bytes) and steer the agent not to re-read. One fewer
call, one fewer failure surface (S264).

**L4 — A uniform bounded observation contract.** Standardize the shape every tool
returns into the loop: `summary` (bounded, always) + `metadata` (counts/paths) +
an optional `detail handle` (fetch full output on demand). This lands in the
observation-ingestion path (`observe.py` / the loop), so bounding is enforced
once, uniformly, rather than re-implemented per tool. The most durable fix; also
the largest.

**L5 (secondary) — Latency budgets.** Audit wall-clock caps on the heavy tools
(shell has 20s; check `browser_agent`, `delegate*`, `best_of_n_edit`,
`process_tool`). Keep latency in perspective: our own traces show tool latency is
usually small next to model thinking — so this is a guardrail against pathological
cases, not the main prize.

## 7. Recommended sequencing

1. **Phase 3a — L1 on `shell` first.** Biggest, safest win; directly kills the
   "context too long" failure class. Measurable in one before/after trace.
2. **Phase 3b — L2 + L3 (steering + drop the redundant read-back).** Cheap prompt
   / guardrail changes; fixes the "explore before create" and "shell for
   discovery" patterns the user flagged.
3. **Phase 3c — L4 (uniform observation contract).** The structural finish that
   makes bounding a property of the framework, not a per-tool patch. Fold L1's
   ad-hoc caps into it.

## 8. Live-verify bar (non-negotiable, per ADR-40 precedent)

Every phase must show a **before/after live trace on z.ai/glm-4.5-flash** (the
active weak model) proving: (a) output-context tokens per turn dropped, and (b)
the task still completes with the right tool selected and valid args — trimming or
re-shaping tool output can regress weak-model behavior; unit tests are NOT enough.
Harness rules stand: isolated `LOCALMIND_HOME`, **never touch port 8000** (the
user's running app), **never print API-key values**.

## 9. Open questions

- L1: fixed token budget vs adaptive (e.g. a directory listing summarizes
  differently than a code diff)? Probably per-tool budgets with a global ceiling.
- L2: prompt-steering vs a hard pre-dispatch rewrite (e.g. auto-route a
  discovery-shaped `shell` command to `find_path`)? Steering first — rewriting
  risks surprising the agent.
- L4: does the observation contract belong in `ToolResult` itself (every tool
  fills a `summary`) or in the ingestion layer (the loop summarizes)? Leaning
  ToolResult, so each tool owns what "bounded" means for its output.
- Does the Thinker get a role here — pre-selecting the tool — or does that
  overload the backbone? Keep it advisory (a hint), not authoritative.

## 10. Relates to

ADR-37 (three-tier routing), ADR-39 (agent-loop token efficiency), **ADR-40 (tool
*schema* input tokens — the INPUT-side sibling of this research)**, ADR-42 (Thinker
— candidate tool pre-selector), S262 ("context too long" — the failure this
prevents), S264 (Windows read-back — a symptom of the redundant read-back in L3).

## CORRECTION (Session 272, Claude Code) — L1 was already implemented; my premise was wrong

Going to implement B-2026-08-16-4 (bound `shell` output, lever L1), I traced the
actual capture path instead of the single return line I had cited — and the
premise collapsed:

- **`shell` already bounds output.** `_capture_process_output` (shell.py:226)
  writes both stdout and stderr into a `BoundedOutputBuffer()` = `TOOL_OUTPUT_MAX`
  **4000 chars**, head+tail, with a `[...TRUNCATED DUE TO LENGTH...]` marker.
  `return ToolResult(content=content)` (shell.py:760) returns that *already-bounded*
  buffer. I had cited line 760 in §4a without following `content` back to line 226.
  **Empirically proven in isolation:** 250,000 chars appended → **4,000** returned
  (`truncated=True`, marker present, head and tail both kept).
- **Every other "raw" tool bounds too:** code_exec (`OUTPUT_MAX` 4000),
  web_fetch (`WEB_FETCH_MAX_CHARS` 8000), git_tool (max_lines + note),
  process_tool (`_MAX_LOG_LINES` 200).
- **There is a SECOND-stage cap.** Every tool observation enters the loop's model
  context through `_truncate_observation(obs, OBS_LOG_MAX_CHARS=2000)` — ~10 call
  sites in loop.py. So output is bounded at two layers: per-tool at the source,
  then again at ingestion.
- **§4a's "fuel behind S262" was wrong.** The S262 "context too long" failure was
  unbounded *thinking* (202s), fixed by `reasoning_effort=low` in S262. Bounded
  shell output (≤4000 chars/call) was not the cause.

**Consequence:** L1 is closed with **no code**. The genuinely-verified remaining
work — grounded in the real traces, not a misread — is **L2 (right-tool steering:
exploratory `ls` before create, `shell` for discovery)** and **L3 (the redundant
