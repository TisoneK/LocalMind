# Review — ADR-40 option C shipped: on-demand long-tail tool loading (describe_tool) (Session 252)

**Agent:** Buffy · **Model:** deepseek/deepseek-v4-flash (per system prompt) · **Date:** 2026-08-16 · **Type:** implementation (B-2026-08-16-2)

## Summary

Implemented ADR-40 **option C** (the hybrid): the 16 long-tail tools are no longer sent in the native `tools` param on every model call. A new **`describe_tool`** meta-tool (the `skill`-loader pattern) loads ONE tool's full schema into the `tools` param for the rest of the run when the model decides it needs that tool. The per-call tool catalog dropped from **16,937 chars (~4,234 tok) to 7,851 chars (~1,962 tok) — a ~54% cut (~2,272 tok/call)** on full-catalog turns; cumulatively vs the pre-ADR-40 24,230 chars that is **~68% smaller (~5,095 tok/call saved)**. **Live-verified on both the active weak model (zai/glm-4.5-flash) and cerebras — the on-demand flow works, core tools still select correctly, and the final-answer truncation seen in the traces is proven pre-existing (baseline-identical).**

## What changed

1. **`core/agent/tool_schemas.py`** — the single source of truth now carries the tier split: `CORE_TOOL_NAMES` (14: shell, file_task, file_write, edit_file, find_path, web_search, web_fetch, code_exec, git, process, memory_op, sysinfo, observe, calculator) vs `LONG_TAIL_TOOL_NAMES` (16: browse, delegate, delegate_parallel, delegate_inline, sql, csv, json, best_of_n_edit, propose_str_replace, propose_write_file, apply_proposed_edit, add_subgoal, update_subgoal, create_plan, skill, diagnostics). New `DESCRIBE_TOOL_DEFINITION` (a separate constant — the 30-tool catalog stays backward-compatible), `long_tail_tool_summary()`, `get_full_tool_def()`, and `tool_defs_for_call()` which composes the per-iteration `tools` param: scoped core defs + describe_tool + the full schemas of any long-tail tools loaded this run, gated by the agent's scope (a scoped agent never gains tools outside its allowed set; a loaded core tool is never duplicated).
2. **`core/models.py`** — `Intent.DESCRIBE_TOOL = "describe_tool"`. **`core/agent/constants.py`** — `describe_tool` added to `AGENT_ALLOWED_TOOLS`.
3. **`tools/describe_tool.py`** (new) — the registered tool: returns the full JSON schema for a long-tail tool with `metadata={"loaded_tool": name}`; an "already always loaded" note for core tools; `not_found` / `validation_error` otherwise. Read-only.
4. **`core/agent/loop.py`** — a per-run `loaded_tools: set[str]` (fresh per run, same pattern as the proposal/subgoal registries). The per-iteration model call (and both prompt builders) now pass `_current_tool_defs()` instead of the static scoped catalog. A tiny `_note_described_tool()` hook runs after EVERY dispatch site (single, parallel, MiniMax-XML, DSML-XML) and records the loaded name from `ToolResult.metadata` — deliberately NOT a contextvar, because `dispatch_with_retry` runs tools inside `asyncio.wait_for`, a child task whose contextvar writes would be lost to the loop. Loaded tools persist for the rest of the run and appear in the next iteration's `tools` param.
5. **`core/agent/text_tools.py`** — `_extract_tool_input` handles `describe_tool`'s single `tool_name` param. Action-label maps gained a "Loading tool docs: X" entry (3 sites).
6. **Tests** — new `tests/core/test_describe_tool_on_demand.py` (11 tests: tier-split integrity, composition incl. scope gating + no-dupes, the tool itself, the metadata-based bookkeeping helper, and an end-to-end AgentLoop stub-adapter test proving call-1 has no `browse`, describe_tool loads it, call-2's `tools` param carries the full browse schema). Updated the 3 existing tests that pinned the old surface: `test_intent_tool_scoping.py` (the param is now scope∩CORE ∪ describe_tool), `test_selection.py` + `test_goal_interpreter.py` (DESCRIBE_TOOL is a meta-tool intent — not a routing intent, no checkable contract).

## Verification (numbers)

- **Size:** full-catalog per-iteration `tools` param: **16,937 → 7,851 chars** (30 → 15 tools incl. describe_tool; ~54% cut, ~2,272 tok/call). Default SHELL intent scope: **9,866 → 7,178 chars** (~27%). With one load (browse): 9,624 chars — the schema is paid only when used. Cumulative vs pre-ADR-40 (24,230 chars): **~68% smaller (~5,095 tok/call)**.
- **Tests:** full backend suite **1,781 passed / 2 skipped / 4 pre-existing env-gated `test_shell.py` failures** (the same 4 as baseline; +11 new tests). Ruff clean on all touched files.
- **Live trace 1 — z.ai/glm-4.5-flash (the ACTIVE weak model):** "list the projects in my home directory" → `mode=execute` → **`shell` fired DIRECTLY** (core — no describe_tool needed), executed and adapted across dirs. Core tools did NOT regress.
- **Live trace 2 — z.ai/glm-4.5-flash, on-demand flow:** "Load the 'python-testing' skill…" → iter 1 the model guessed `skill({"name": …})` (wrong param — skill not yet loaded, degenerate-input rejected) → iter 2 **`describe_tool("skill")`** (log: `describe_tool loaded 'skill' for this run`) → iter 3 **`skill({"skill_name": "python-testing"})`** executed with the full skill content → final answer started. The exact ADR-40 C flow (describe → then call with valid args) worked on the weak model, including self-correction after the first-guess rejection.
- **Live trace 3 — cerebras/gpt-oss-120b (capable provider, temp LOCALMIND_HOME, keys copied to disk and deleted after, never printed):** iter 1 **`describe_tool({"tool_name": "skill"})`** — no wrong guess — loaded; the follow-up synthesis hit cerebras's documented tokens-per-minute quota (Session 251's exact limit), handled by the Session 241 evidence-preservation path (`agent_loop_degraded`, evidence preserved). Tool selection itself verified clean.

## Honest limits / pre-existing findings (NOT regressions)

- **Weak-model final-answer truncation is PRE-EXISTING:** both live traces stopped at ~62–74 chars mid-sentence ("…it covers LocalMind's"). I re-ran the SAME two tasks against the stashed baseline (HEAD = Session 251): BASE A truncated identically (74 chars) and BASE B truncated too (65 chars, "The python-testing skill is named **"). This is the zai free tier's output budget, unchanged by option C.
- **`agent_loop_failure: tool_failure` after a successful adapted run is pre-existing semantics:** `classify_failure()` returns `tool_failure` whenever ANY step has `tool_failed=True`, even if the run then succeeded. Trace 2's iter-1 rejected guess flagged it; the baseline's own adapted shell trace would flag the same. Failure memory may record noise for such runs — worth a future cleanup (e.g. only classify tool_failure when the LAST step failed), but out of scope here.
- **The on-demand round trip is real latency:** a tool's first use in a run costs one extra model call (describe_tool). Loads persist per run, so multi-step use pays it once. This is the ADR's accepted tradeoff for C ("prefer B/C there").
- One of the two canonical tasks in the live runs hit the `token_leak` anomaly heuristic (fresh sessions with near-identical context sizes) — a known false-positive pattern for short system-prompt-similar turns, not caused by this change.

## Open items

- **ADR-40 option A** (full dynamic schema injection) is now explicitly unnecessary — C already delivers the ~90% theoretical reclaim; reserve A only if a future measure shows the long tail still matters.
- ADR-37 follow-ups (B-2026-08-15-10/11/12) and other pre-existing backlog items unchanged.

## Recommended next steps

1. Consider the `classify_failure` cleanup (only flag `tool_failure` when the failing step is terminal) so adapted runs don't poison failure memory.
2. Re-verify the on-demand flow on a REAL multi-step long-tail task (e.g. a git-free browser task on a machine with `agent-browser` installed) to confirm the describe→use→continue loop across several iterations.
3. Optionally surface the catalog size in observability so future token work has a live baseline (already suggested in review-41).
