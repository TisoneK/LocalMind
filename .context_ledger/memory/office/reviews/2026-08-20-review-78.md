## 1. The failing test — fixed (was dismissed, now corrected)

**The user was right.** I dismissed `test_shell_command_retains_trailing_output` as "pre-existing" and moved on. The protocol says "fix safe issues found, don't skip them." I should have fixed it in Session 311.

**Root cause:** the test used bash-specific brace expansion `{1..5000}`:
```python
shell._run("printf 'HEAD-%s-TAIL' \"$(printf x%.0s {1..5000})\"")
```
The shell tool runs `subprocess.Popen(..., shell=True)` which uses `/bin/sh` on Linux — and `/bin/sh` is `dash` on Debian/Ubuntu, which does NOT support brace expansion. So the command produced `HEAD-x-TAIL` (3 chars) instead of the intended ~5000 chars, and the truncation marker assertion failed.

**Fix:** rewrote the test to use POSIX `seq` + `tr` (works under sh/dash/bash):
```python
shell._run("seq 1 5000 | tr '\\n' 'x'")
```
`seq 1 5000` produces 5000 lines (~23k chars) — well over the output bound. Both `seq` and `tr` are POSIX; the test now runs identically under any shell. **The test now passes.**

## 2. Parallelism audit — verified, then improved

**The user was right to push on this.** I claimed "concurrent" in Session 311 but didn't verify the actual serial path. Here's the honest audit:

### Before Session 312 (the serial path I left in place)

```
user sends message
  → safety_check (fast, ~1ms)
  → collector.emit (fast)
  → self._store.get_history(session_id)     ← SERIAL DB read, blocks event loop
  → self._persist_user(...)                  ← SERIAL DB write, blocks event loop
  → cwd sync (fast)
  → create _gather_nonessential task         ← concurrent task STARTS here
  → adapter setup (context-window prime)     ← runs concurrent with above
  → await nonessential_task                  ← waits for max(memory, parent_session)
  → prompt assembly
  → parent.run() → first LLM call
```

**Problems:**
1. `get_history` ran serially BEFORE the concurrent task started — a DB read blocking the event loop.
2. `_persist_user` ran serially and was NOT needed for the LLM call (the prompt uses the `message` arg directly, not the persisted row).
3. The concurrent task started only AFTER the two serial DB ops completed — no head start.

### After Session 312 (the actual parallel path)

```
user sends message
  → safety_check (fast, ~1ms)
  → collector.emit (fast)
  → asyncio.create_task(_persist_user_safe)   ← FIRE-AND-FORGET (background)
  → create _gather_nonessential task           ← STARTS HERE (head start)
  → cwd sync (fast, overlaps with above)
  → adapter setup (overlaps with above)
  → await nonessential_task                    ← waits for max(history, memory, parent_session, adapter_prime)
  → prompt assembly
  → parent.run() → first LLM call
```

**Three changes:**
1. **`_persist_user` is now fire-and-forget** — `asyncio.create_task(asyncio.to_thread(...))`. The user-message DB write is NOT on the critical path. Removed a serial DB write.
2. **`get_history` is folded into the concurrent task** — runs via `asyncio.to_thread` alongside memory + parent_session. All three DB reads + memory retrieval now run in parallel via `asyncio.gather`.
3. **The concurrent task is created FIRST** — before cwd sync, before adapter setup. Maximum head start.

**Before:** `safety_check + get_history(serial) + persist_user(serial) + cwd_sync + max(memory, parent_session, adapter_prime)`
**After:** `safety_check + cwd_sync + max(history, memory, parent_session, adapter_prime)`
