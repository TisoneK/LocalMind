## Executive Summary

All three claims were grounded against the current code plus a live trace on
bankofai/deepseek-v4-flash. Two are resolved non-issues on the current build; the third is a real,
previously-unseen architectural regression: **the Todos panel can never populate in the warm-kernel
runtime**, because ADR-52 Phase 1 (warm parent kernel) retired the per-turn init call and nothing
replaced the plan→todo production. This is the root cause of the user's empty-panel observation and
explains why the model "thinks in checklists" — its steps have no todo UI to land in.

## Findings

1. **"file_task can't resolve relative paths" → already fixed (Session 325).** The bare-path
   extractor now keeps Windows-relative backslash paths whole, and resolution tries home/ then cwd/
   (first existing candidate). Unit-proven. The successful Windows run used ABSOLUTE paths
   (`C:\Users\tison\Dev\test-run\notes.txt`) and forward-slash mkdir, so it exercised Session 264's
   absolute handling, not S325's relative path — the user's own "this is incidental, not a real fix"
   read is correct. Confirmation = a fresh-chat run that goes straight to a relative path (needs the
   user's Windows box; macOS cannot faithfully test Windows separator semantics).
2. **"Keep JSON concise." in Thinking → NOT the Thinker leak.** The string does not exist in the
   codebase. The planner prompt says "Respond with a concise plan in this format" (prompts.py:207)
   and the init prompt asks for a `plan` field — the line is the model echoing its own instructions
   during genuine reasoning, which is normal thinking-stream content. The trace containing it
   predates the Session 324 restart (it is the same trace that carried the full Thinker monologue).
   Current build live-verified: the Thinker consult ran (agent_thinker_start/done) with **0 marker
   hits across all thinking tokens** — S324 holds.
3. **Checklist-shaped thinking = model behavior (user is right).** Not a routing bug — deepseek
   free-tier narrates audience-aware status checklists instead of deep reasoning ("narration-as-
   theater"). No code lever changes what a model thinks; the panel fix below is what makes the
   checklist land somewhere useful.

## Root cause found: empty Todos panel is structural (B-2026-08-20-23)

- `agent_runtime.py:917` is the only production call site of `parent.run()` and hardcodes
  `skip_planning=True` (ADR-52 Phase 1 warm kernel retired the per-turn JSON initializer).
- `loop.py`'s three plan→todo branches are all gated on `not skip_planning` (parent-init ADR-49
  branch ~1238, non-parent plan-stream ~1312) or on caller-injected `plan_steps` (~1334 — the
  runtime passes none).
- The only remaining emission path is the `todo_write` TOOL (loop.py:346), which requires the model
  to voluntarily call it — ADR-49's own evidence shows free-tier models ignore todo_write even when
  prompted (glm-4.5-flash live-fail).
- Live trace reproduced it: `plan=no-plan`, `criteria=0`, **0 todo_created**, no planning events, on
  the current build. The turn also stopped after mkdir (72-char answer, no file) — free-tier
  premature-stop variance, unrelated to the panel issue.

## Fix direction (user decision required)

The user's ADR-49 directive was "todos = the actual steps planned BEFORE, followed one after another
until finished" — i.e., upfront. The warm kernel removed the call that produced the upfront plan.
Options: (A) restore an upfront plan in the warm-kernel first call (ADR-49 intent, model-dependent
again); (B) harness-derive todos from the tool sequence as it runs (deterministic, model-agnostic,
but post-hoc); (C) both — upfront when the model cooperates, tool-derived fallback. Pending the
user's call; no code changed this session.

# Follow-up (same session): harness-owned synthesized todos shipped (B-2026-08-20-23 done)

The user's design input resolved the open direction: "a todo describes what happened; a plan
constrains what's allowed to happen next, before it happens" — and the user-facing todo "can exist
as a separate, later-rendered artifact generated from this plan's outcomes, but it should never be
what the model is doing instead of this." That is harness-owned todos derived from actual tool
executions (option B), with the model's internal planning left to the model (and the existing
task-anchored nudge machinery steering it toward acting).

**Shipped (`a0e43f3`):** `loop.py` synthesizes one todo per real tool execution when no plan-based
steps exist:
- `_synth_begin()` — before the tool_call started emit: emits `todo_created` (id `syn-N`, text
  distilled from the tool call via `_synthetic_todo_text`, status in_progress); returns the id.
- `_synth_end()` — after the tool lands: emits `todo_completed` (skipped on failure, so failed
  steps stay pending for the turn-end finalize).
- Wired into ALL THREE dispatch paths (main single-tool, second single-tool, parallel batch — the
  batch keys ids by call index). describe_tool excluded (`_SYNTH_SKIP`), bounded at 12, and
  `_synth_begin` returns None whenever `_plan_steps` is non-empty so a plan-based checklist never
doubles.
- `todo_id` on the tool_call events now carries the syn id so the frontend can tie cards to todos.

**Tests (`tests/core/test_synthesized_todos.py`, 4):** warm-kernel tool turn emits syn-0 created +
completed with a Run: label and no plan- ids; describe_tool produces no todos; a plan-based init
(plan_steps) yields plan-0/plan-1 with NO synthetic duplicates; label distillation unit checks.

**Live-verified (bankofai/deepseek-v4-flash, isolated 8765):** the same create-test-run task —
`todo_created` syn-0 "Run: mkdir -p test-run" and syn-1 "Write: /Users/bao/test-run/notes.txt:"
each followed by `todo_completed`; 4 describe_tool calls produced no todos; the task completed
(19-byte notes.txt with the exact content). One earlier attempt stopped after describe_tool
(free-tier premature-stop variance, unrelated).

**Baseline:** full backend **2087 passed / 2 skipped / 0 failures** (2083 + 4 new); ruff clean
(one accidental line-merge in the emit blocks caught by ruff and fixed).

**Notes:** ADR-49's original "upfront plan" directive is NOT restored — the harness-derived surface
supersedes it per the user's new framing. If the user later wants the pre-task plan visible again,
that is a separate follow-up (upfront plan in the warm-kernel first call) layered on top. The
